## 2. Gate law

The two changes form one gate:

1. CF-08 must make every emitted C# union representation sound for the accepted schema.
2. CF-09 must prove that the exact generated bytes are committed in the actual Unity consumer
   repository at an immutable commit.

The governing laws are:

- Preserve JSON nullability separately from property presence.
- Emit a compatible aggregate only when compatibility has been proved recursively.
- Emit a discriminated representation only when the discriminator is closed and unambiguous.
- Fail before any output write for every unsupported or incompatible union.
- Never select the first member as a type policy.
- Never erase a type, presence, nullability, or requiredness conflict.
- Never accept a TypeScript-local copy as proof of the Unity consumer.
- Never require a commit to contain its own future commit SHA.
- Never hand-edit generated DTOs.

### 3.2 The exact unsound flattening

objectShape currently:

1. recursively resolves object and anyOf branches;
2. unions every property name across the branches;
3. gathers candidates only from members that declare that property;
4. merges only multiple direct const values into a vocabulary;
5. otherwise assigns candidates[0] as the property schema;
6. widens that selected schema only when another direct candidate is nullable;
7. marks the property required only if every branch marks it required.

It does not compare reference targets, primitive kinds, arrays or item types, nested objects,
enum constraints, property presence, nullability, or requiredness. The result silently encodes
facts that no source member permits and fails to encode facts that valid members require.

Concrete accepted-schema damage:

- StudioProductionCommandSnapshot is a three-member kind-discriminated union. Its aggregate makes
  directorId optional, admits assign-without-directorId, and admits clear/schedule-with-directorId.
- StudioBridgeQuoteRequest has commission and casting members whose draft references are
  incompatible. The aggregate draft is silently StudioCommissionDraftPayload, so valid casting
  requests cannot be represented through the aggregate.
- StudioQuoteSnapshot flattens commission and casting responses. Member-only required fields
  become optional, subtype identity is lost, and its generated kind vocabulary contains only the
  first commission member's values. A narrow nullable noFeeLine adjustment does not make the
  aggregate sound.

### 3.4 Serializer behavior today

Generated classes use JsonObject(MemberSerialization.OptIn). Property attributes currently map:

| Schema presence/nullability | Json.NET attribute |
|---|---|
| required, non-null | Required.Always |
| required, nullable | Required.AllowNull plus Include |
| optional, non-null | Required.DisallowNull plus Ignore |
| optional, nullable | Required.Default plus Ignore |

CreateStrictJsonSettings uses MissingMemberHandling.Error, included null/default values,
ObjectCreationHandling.Replace, TypeNameHandling.None, invariant culture, trailing-content
checking, depth 128, and StringEnumConverter. Arrays initialize to Array.Empty of the item type.

CF-08 preserves these strict settings but must stop conflating JSON nullability, CLR value-type
syntax, and required presence. Any optional array/default-emission behavior must be pinned by
fixtures; it must not be used to hide a union conflict.

### 3.5 Partial-write defect

The current CLI constructs an array containing asynchronous schema output operations before
generateCsharp is fully evaluated. An analysis exception can therefore race an earlier write.
The new flow must:

1. parse and analyze the whole schema;
2. render schema, C#, and manifest fully in memory;
3. run check-only comparisons, or stage every write in same-directory temporary files;
4. publish by atomic rename only after every staged output is valid.

No negative fixture may invoke an output sink.

## 4. CF-08 union taxonomy and exact policy

Classifier priority is A nullable, then C discriminated, then B compatible. Everything else is D
or E and fails.

| Class | Supported | Generated representation | Serializer behavior | Fail-closed condition | Required fixtures |
|---|---|---|---|---|---|
| A. T or null | Yes, only exactly one non-null and one direct null arm | Underlying T; nullable value marker for value types; required nullable reference uses AllowNull/Include | Null and T round-trip; missing still fails when required | Any other null/non-null arm count; nullable wrapper around an unsupported union | F01, F02, branch-order reversal |
| B. compatible object union | Yes, only closed objects with identical property set, presence, requiredness, nullability, and recursive storage signature | One sealed aggregate; no converter | Ordinary strict DTO; every member is representation-equivalent | Any property/ref/array/nested/constraint signature differs | F03 plus reorder |
| C. discriminated object union | Yes, only named closed object references with one shared required non-null string discriminator and non-empty pairwise-disjoint const/enum values | Abstract named union base excluding the discriminator; sealed concrete members each own and validate their exact discriminator domain; deterministic exact-base converter; complete vocabulary | Converter rejects duplicate/missing/non-string/unknown discriminators and dispatches before materialization; concrete assignment/deserialization and OnSerializing validation make outbound JSON sound | Missing/ambiguous discriminator, overlapping/empty values, unnamed/open member, invalid outbound value, multiple-base inheritance conflict | F04, F09 positive, F10, F11, F12 |
| D. incompatible object union | No | None | None | Type, presence, requiredness, nullability, ref, array-item, nested-shape, or unreflected constraint conflict without a safe discriminator | F05, F06, F08 |
| E. primitive/object mixed or general non-null primitive union | No; closed primitive vocabulary must use enum/literal instead | None | None | Member kinds are mixed or cannot be represented by the supported enum/literal path | F07, F09 negative |

There is no loosest-wins row. Namedness alone is not support.

### 5.2 Likely types and signatures

~~~ts

type SchemaPath = string; // RFC 6901 JSON Pointer

interface GeneratorContext {
  readonly root: Schema;
  readonly definitions: Readonly<Record<string, Schema>>;
}

interface CSharpStorage {
  readonly text: string;
  readonly kind: "string" | "bool" | "int" | "double" | "array" | "object" | "union";
  readonly nullable: boolean;
  readonly signature: string;

type UnionPlan =
  | { readonly kind: "nullable"; readonly nonNull: CSharpStorage }
  | { readonly kind: "compatible-object"; readonly name: string; readonly shape: ObjectPlan }
  | {
      readonly kind: "discriminated-object";
      readonly name: string;
      readonly discriminator: string;
      readonly cases: readonly DiscriminatedCasePlan[];
    };

class CSharpContractGenerationError extends Error {
  readonly code: string;
  readonly schemaPath: SchemaPath;
}

function splitNullableUnion(schema: Schema, path: SchemaPath):
  { readonly nonNull: Schema; readonly nullable: true } | null;
function resolveSchema(schema: Schema, path: SchemaPath, context: GeneratorContext): ResolvedSchema;
function analyzeCSharpStorage(schema: Schema, path: SchemaPath, context: GeneratorContext): CSharpStorage;
function analyzeObjectMember(schema: Schema, path: SchemaPath, context: GeneratorContext): ObjectMemberPlan;

function analyzeContract(schema: Schema): ContractPlan;
function generateCsharpContract(input: GenerateContractInput): string;
function emitCompatibleClass(plan: CompatibleObjectPlan): string;
function emitDiscriminatedBase(plan: DiscriminatedObjectPlan): string;
function emitMemberClass(plan: DiscriminatedCasePlan): string;
function emitUnionConverter(plan: DiscriminatedObjectPlan): string;
~~~

All recursive functions carry the use-site JSON Pointer and the resolved-definition pointer.
Unknown references and cycles fail with both pointers. Storage signatures include exact referenced
definition name, array item signature, nullability, and supported constraints; two references are
not compatible merely because both spell as a C# class.

### 5.3 Analysis pseudocode

~~~text
analyzeContract(root):
  validate root and local definitions
  for each definition in ordinal order:
    recursively analyze every property, array item, reference and union
  validate C# identifier and inheritance collisions
  return immutable ContractPlan

analyzeUnion(schema, path):
  if exact nullable form:
    analyze the sole non-null member
    reject if the inner member is unsupported
    return NullablePlan

  require a named non-null union
  resolve every member and classify its kind
  if kinds are not all closed objects:
    fail CF08-MIXED-UNION

  inspect all shared required, non-null string const/enum properties
  calculate which candidates have non-empty pairwise-disjoint value sets
  if x-csharp-discriminator metadata exists:
    validate it first as a non-empty string
    require it names one of the shared candidates and that candidate is safe
    require named referenced members and valid single-base ownership
    return DiscriminatedObjectPlan for that explicit candidate
  if exactly one safe candidate exists:
    require named referenced members and valid single-base ownership
    return DiscriminatedObjectPlan for that inferred candidate
  if more than one safe candidate exists:
    fail with the exact ambiguous-candidate diagnostic
  otherwise continue to compatible-object analysis

  compare exact property sets, presence, requiredness, nullability and storage signatures
  if all are equal:
    return CompatibleObjectPlan
  fail CF08-INCOMPATIBLE-OBJECT-UNION at first ordinal mismatch

generate:
  analyze entire contract
  emit from ContractPlan only
  build every target byte string in memory
  check all targets or atomically publish all targets
~~~

Branch order may never select a property type. Diagnostics sort member kinds and compare properties
in ordinal wire-name order. Discriminated case/vocabulary order follows the documented schema
member order; definitions/classes remain ordinal. The same input must produce byte-identical
output twice.

### 5.4 Discriminated C# representation

Generated output adds using System.Runtime.Serialization for OnSerializing, OnDeserialized, and
StreamingContext; fully qualified names are an acceptable byte-equivalent policy if pinned by the
golden. For an explicit shared kind union, emit this shape:

~~~csharp
public abstract class ProbeUnion
{
    // Only identical non-discriminator fields belong here.
}

public sealed class ProbeAlpha : ProbeUnion
{
    private const string ExpectedKind = "alpha";
    private string kindValue = ExpectedKind;

    [JsonProperty("kind", Required = Required.Always)]
    public string kind
    {
        get => kindValue;
        private set
        {
            if (!String.Equals(value, ExpectedKind, StringComparison.Ordinal))
                throw new JsonSerializationException(
                    "C# union ProbeUnion member ProbeAlpha requires discriminator kind=alpha.");
            kindValue = value;
        }
    }

    [OnSerializing]
    private void ValidateUnionMember(StreamingContext context)
    {
        if (!String.Equals(kindValue, ExpectedKind, StringComparison.Ordinal))
            throw new JsonSerializationException(
                "C# union ProbeUnion member ProbeAlpha requires discriminator kind=alpha.");
    }
}

public sealed class ProbeBeta : ProbeUnion
{
    // Owns an equivalent beta-only validated discriminator property.
}
~~~

The converter:

- CanConvert only when objectType equals the exact union base;
- CanWrite is false;
- is registered deterministically in CreateStrictJsonSettings rather than attached as an
  inheritable attribute to every concrete member;
- reads one JObject with JsonLoadSettings.DuplicatePropertyNameHandling.Error, requires exactly one
  discriminator property as a string, and dispatches through a generated closed map;
- populates the concrete generated member with the same strict serializer;
- throws for missing, null, non-string, unknown, duplicate, or ambiguous discriminators;
- never enables TypeNameHandling;
- never treats a member-only field as a discriminator;
- serializes the runtime concrete DTO without adding a synthetic type field; every concrete member
  validates its discriminator again on assignment/deserialization and OnSerializing.

Only properties whose presence, requiredness, nullability, and recursive storage signatures match
in every case may be promoted to the base. The discriminator is always excluded from promotion,
even though its CLR storage kind is string. A const member gets a constant-initialized property
with a validating private setter. A multi-value enum member gets a setter restricted to its own
closed values. That setter is public for legitimate outbound construction, its backing value starts
unset rather than choosing a semantic default, and OnSerializing fails until an allowed value has
been assigned. OnDeserialized and OnSerializing revalidate it. A generated helper/factory may
centralize assignment but may not bypass validation. Member-only or conflicting fields stay on
members.
Each variant definition may inherit at most one generated union base; otherwise generation fails
until the schema is deliberately modeled another way.

### F01 — string or null

Schema fragment:

~~~text
Holder.value = anyOf [{ type: string }, { type: null }]
Holder.required = [value]
~~~

- Expected C#: Holder.value is string with Required.AllowNull and NullValueHandling.Include. No
  union class or converter is emitted.

### 9.2 Two verification modes

Seal mode requires:

- each supplied root realpaths to git rev-parse --show-toplevel;
- canonical remote repository identity;
- HEAD equals the supplied 40-character commit;
- expected ref resolves to that commit;
- tracked, staged, unstaged, and untracked status is empty;
- expected commits exist locally and on the intended remote before final seal;
- every consumer path component is nonsymlinked and contained;
- Git mode is exactly regular blob 100644;
- the committed TS schema/C#/manifest and committed Unity consumer agree.

Immutable-attestation mode:

- reads files directly from referenced commit objects;
- does not require current HEAD to remain on the old attested commit;
- revalidates repository, commit existence, manifest hash/closed fields, versions, paths, and both
  committed C# hashes;
- creates a disposable isolated checkout of typescriptSourceCommit, verifies its canonical
  generator-source bundle and lockfile against generatorSourceSha256, and runs the generator from
  that checkout in check-only mode. It never uses the current checkout's generator to attest a
  historical commit;
- records and verifies the external verifier's own source/tool hash as verifierSourceSha256;
- receives both Git roots explicitly, validates their canonical repository identities, and reads
  the referenced commit blobs from those object databases regardless of either root's current
  HEAD; a missing referenced object fails rather than falling back to worktree bytes;
- receives the retained G5 XML and log explicitly, requires their canonical artifact-relative
  names, hashes their exact bytes, and checks those paths/hashes against the attestation; reverify
  resolves those names only beneath an explicitly supplied evidence root and rejects redirection;
- never changes either repository.

Repository identity normalization accepts only the configured canonical GitHub HTTPS/SSH forms
that normalize to the exact owner/repository slug. A filename, Unity marker, or coincidentally
matching content is insufficient.

### 9.3 Path and commit verification algorithm

~~~text
preflight root:
  realpath supplied root
  obtain git top-level; require exact realpath equality
  normalize configured remote; require expected repository slug
  reject dirty tracked, staged, unstaged, or untracked paths
  require exact HEAD and expected ref when in seal mode

preflight path:
  parse manifest as closed canonical JSON
  require allowlisted relative path
  walk each component with lstat; reject every symlink
  realpath parent and target; require containment
  require git mode 100644 at the referenced commit

verify immutable objects:
  require git cat-file -e COMMIT^{commit}
  read manifest and TS C# from the TypeScript commit object
  read Unity C# from the Unity commit object
  create a test-owned isolated checkout of the TypeScript commit
  verify the exact generator source bundle and lockfile from that commit
  run that commit's generator in check-only/no-write mode
  independently derive schema identity and generated expected C# there
  SHA-256 committed bytes
  require generated expected = TS committed = Unity committed
  require manifest versions/paths/hashes = independently derived facts
  emit attestation outside both roots only after all checks pass
~~~

Do not use a moving branch as content authority. A ref is a seal-time assertion; the immutable
40-character commit and its blobs are the lasting proof.

The disposable checkout has an explicit temporary root, exact commit, clean pre/post status, and
bounded cleanup. If the attested generator or its locked runtime cannot be executed, immutable
regeneration fails closed; generatorVersion alone never substitutes for source identity.

### 9.4 Correct seal sequence

1. Generate the pretty schema, TypeScript C#, and deterministic manifest fully in memory.
2. Run CF-08 fixtures and TypeScript-local contract checks.
3. Commit generator, tests, outputs, and manifest in TypeScript.
4. Push and record the existing TypeScript commit.
5. Copy only exact generated C# bytes to the fixed Unity consumer.
6. Update bounded Unity consumers/tests for the new generated type shape.
7. Commit and push the Unity consumer commit.
8. Verify two isolated clean worktrees at those exact commits.
9. Run the one authorized Unity batch compile/focused EditMode pass.
10. Complete the fresh hostile review and dispose every upheld blocker through its owning wave.
11. Produce an attestation outside both repositories.
12. Reverify it from immutable commit blobs.
13. Store it as an immutable CI artifact or later documentation/attestation commit.
14. Never amend either attested commit to insert its own SHA.

### 10.2 Required failure tests and stage

| Failure fixture | First required failure | Exact assertion | CI obligation |
|---|---|---|---|
| Wrong Unity repository | Before generation, paired-root preflight | CF09_REPOSITORY_MISMATCH even if markers, file, and bytes match | Checkout repository slug must be independently pinned |
| Wrong Unity root | Before generation, root preflight | CF09_ROOT_NOT_TOPLEVEL when supplied realpath differs from Git top-level | Fail before reading the consumer |
| Wrong generated-file path | Before generation, manifest/path validation | CF09_PATH_INVALID for any noncanonical/nonallowlisted path | Closed manifest schema |
| Stale generated Unity file | During consumer verification | CF09_CONSUMER_HASH_MISMATCH against committed blob | Three-way expected/TS/Unity comparison |
| One-byte uncommitted consumer drift | Before generation in seal-mode clean check | CF09_UNITY_DIRTY; hash equality cannot excuse dirt | Include untracked and index state |
| One-byte committed consumer drift | During consumer verification | CF09_CONSUMER_HASH_MISMATCH with expected/observed SHA-256 | Read commit object, not worktree |
| Schema ID mismatch | During generation/manifest consistency | CF09_SCHEMA_MISMATCH against independently derived identity | Recompute; do not trust manifest |
| Protocol mismatch | During generation/manifest consistency | CF09_PROTOCOL_MISMATCH across schema, generated constant, manifest | Pin exact integer |
| Projection mismatch | During generation/manifest consistency | CF09_PROJECTION_MISMATCH across schema, generated constant, manifest | Pin exact integer |
| Dirty TypeScript tree | Before generation in seal mode | CF09_TYPESCRIPT_DIRTY for staged, unstaged, or untracked path | Clean checkout and post-check status |
| Dirty Unity tree | Before generation in seal mode | CF09_UNITY_DIRTY for staged, unstaged, or untracked path | Clean checkout and post-check status |
| Missing consumer | During consumer verification | CF09_CONSUMER_MISSING when commit lacks regular blob at fixed path | No fallback filename search |
| Manifest has commit field | During manifest validation | CF09_MANIFEST_MISMATCH unknown recursive metadata | Enforce closed keys |
| Manifest refers to nonexistent commit through attestation | During attestation | CF09_COMMIT_NOT_FOUND from commit-object existence check | Fetch exact SHA then fail if absent |
| Manifest hash does not match commit contents | During attestation | CF09_ATTESTATION_HASH_MISMATCH before Unity parity acceptance | Hash manifest blob from TS commit |
| TS copy matches itself but actual Unity differs | During consumer verification | CF09_CONSUMER_HASH_MISMATCH despite local check passing | Mandatory Unity checkout |
| Symlink/path redirection | Before generation, path preflight | CF09_PATH_REDIRECTED for any symlink component or mode 120000 | lstat walk plus Git mode check |
| Wrong branch with coincidentally matching filename | Before generation in seal mode | CF09_HEAD_MISMATCH or CF09_REF_MISMATCH before bytes | Pin ref and 40-character commit |
| Same bytes at wrong commit | Seal verification/attestation | Exact commit mismatch; content equality is insufficient | Record immutable commit/tree |
| Spoof repository with matching local copy | Before generation/CI | CF09_REPOSITORY_MISMATCH | Verify canonical remote and remote commit reachability |
| TS or Unity changes after successful worktree check | During immutable attestation | Committed blob/hash mismatch exposes post-check gap | Attest only existing pushed commits |
| Generator source/version spoof | Manifest and immutable attestation | CF09_GENERATOR_SOURCE_MISMATCH when canonical bundle from the attested TS commit differs | Regenerate only with the exact attested source/lockfile |
| One-byte drift in scripts/bridge-contract-consumer-lock.ts or scripts/verify-bridge-contract-consumer.ts | Attestation verification | CF09_VERIFIER_SOURCE_MISMATCH after recomputing the closed four-path CF09_SOURCE_BUNDLE_V1 envelope from the executing verifier source | Record and rederive the trusted verifier source hash; never accept the attestation value as its own proof |
| Fixture module/generator differs from attested corpus | Immutable verification | CF09_FIXTURE_SOURCE_MISMATCH | Hash the exact shared module and test-only generator from the TS commit |

Negative tests create bounded temporary repositories with explicit commits, modes, remotes, and
worktree states. They never point at an Owner worktree. Cleanup removes only the exact test-owned
temporary directory.
