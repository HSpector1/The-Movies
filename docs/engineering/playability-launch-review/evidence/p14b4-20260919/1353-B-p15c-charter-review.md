# Independent review 1353-B

Subject: `docs/engineering/playability-launch-review/evidence/p14b4-20260919/1353-A-p15c-finale-legacy-charter.md` (P15C 2040 finale / Legacy dossier / post-2040 sandbox charter, Wave 1 pure-law detail). Read-only review against repo HEAD 895df584. No shell/write access used; all findings below are from `Read`/`Grep`/`Glob` against the cited files.

**VERDICT: REFINE**

The charter is unusually well-grounded — every file:line citation I spot-checked (≈30 across `calendar.ts`, `tick.ts`, `hollywoodTick.ts`, `hollywoodTypes.ts`, `types.ts`, `releaseCareers.ts`, `hollywoodValidation.ts`, `receptionVerdict.ts`, `technologyCatalogue.ts`, `technologyTypes.ts`, `bridge/industry.ts`, `bridge/history.ts`, `bridge/session.ts`, `bridge/testing/c3-active-endurance-contract.ts`, `ui/src/engine/adapter.ts`, `ui/src/lot/livingTurn.ts`) matched exactly, down to the line. Ruling compliance (no invented Honors/score/winner, 2040 freeze, sandbox failure risk, P16 boundary) is real and testable, not asserted. But this is a "Wave 1 pure law" charter whose whole job is to remove ambiguity before a test author writes RED, and I found four concrete, bounded gaps in the archetype predicates (§5.3) that leave exact arithmetic or partitioning undefined where the charter's own stated convention (spelled out integer products for every money predicate) says it should be defined. These are cheap, textual fixes, not a redesign — hence REFINE, not REJECT.

Verified against source: `blueprintRequirements.ts:68` ("Awards are not part of the game yet.") and `bridge/history.ts:497-498` (`recordsAvailable: false`) both confirmed byte-for-byte.

- Ruling 3 end-of-run record: §7, see item 6 below — sound in shape, but dependent on an unadopted sibling charter (flagged, not blocking here).
- P15B/P16 boundaries: none of the 8 archetypes touch acquisition/valuation/mergers; `resilient-survivor` correctly treats P15B's condition stream as an external dependency rather than reimplementing distress law.

The claim "releases in the tick producing W carry W−1" is exactly correct, and the boundary-cut design ("6240 ranking inside, 6253 not") follows from it soundly.
- In-run-at-B treatment: verified against `bridge/industry.ts:65-68` — gross-to-date for an active run IS already public (`liveRun.cumulativeGrossPaid`), full total only once settled; the charter's decision to still exclude it from the manifest ("only gross-to-date is public... no gross of it enters the manifest") is a conservative, correct reading, not a leak.

My initial suspicion that snapshotting `standingAtBoundary` per rival might newly expose a private fact is refuted by source: Standing has never been privacy-protected here, only cash/cost/revenue are (§5.1's table correctly marks those "Never read").

**3. No-backfill/completeness** — MET WITH EVIDENCE for the drop decisions; PARTIAL / open for the Q4 lens question.
- Dropped-rival-gross reasoning checked against `hollywoodTick.ts:373-378` (settlement discards the running `weeklyGross` array, keeps only `studioRevenueReceived`/`settledWeek`) — confirmed exactly, and no archetype in §5.3 needs the intra-run curve.

- Q4 (Standing trend lens): my ruling is **do not add it now**. None of the fixed 8 archetypes or the 8 v1 lenses needs a Standing trajectory (the `ranking` lens is explicitly Standing-independent per 1350-A's own `rank-standing-independent` test). Standing drift has never had a receipt regardless of P15C (`hollywoodTick.ts:379-380`, no `appendReceipt` call — pre-existing behavior), so deferring this introduces no *new* loss. If a future lens wants a Standing trend, it's a new versioned law like any other addition, not something Wave R needs to rescue today.

**4. Archetype predicates §5.3** — PARTIAL. Symmetric/deterministic/no-role-flag/no-privacy-leak framing is sound and verified (see below), but four concrete drafting gaps remain:

- **Defect 1 (blocking for RED authoring):** `audience-institution`'s "at least half ≥ LEGACY_AUDIENCE_LIKED_MIN" (1353-A:161) has no exact integer inequality, unlike every money-based predicate in the same table which spells out an exact product (e.g., `artistic-voice`'s `100a ≥ P×n`, `commercial-engine`'s `100×gross ≥ P×baseMarketValue`). *Fix:* state the rule as `2 × likedCount ≥ scoredReleasesInDecade` (or whichever rounding direction is intended) directly in §5.3.
- **Defect 2 (blocking):** `genre-specialist`'s "one genre holds more than half the releases" (1353-A:165) has the same gap. *Fix:* state `2 × genreCount > n` explicitly.
- **Defect 3 (blocking):** `audience-institution`'s "decade" is never partitioned. It's not obvious whether a "decade" is a calendar block (1920-1929, 1930-1939, …) or a rolling 520-week window from studio entry, and this materially changes results for studios entering mid-decade. *Fix:* one sentence naming the exact partition (calendar blocks are the natural reading given every other cadence in this codebase is calendar-anchored, but it must be stated, not inferred).
- **Defect 4 (blocking):** `technology-pioneer`'s contrary clause, "first operational later than `commercialWeek + LEGACY_TECH_LATE_WEEKS` (adoption ID)" (1353-A:163), is ambiguous between "S's own earliest adoption record of that technology" and "the industry's first adoption of it." The common rule ("reads one studio's facts... never another studio's result") strongly implies the former, but a test author could reasonably misread it as the latter, which would break the whole predicate's symmetry guarantee. *Fix:* say "S's own earliest operational adoption" explicitly.

None of these are architectural problems — they're specification gaps in a document whose entire stated job (§0/§9) is to remove exactly this kind of ambiguity before RED authoring. Given this project's own documented history of reconciliation bugs from under-specified "exact" laws, I'm treating these as blocking for 1353-F adoption, not merely stylistic.

Confirmed sound and correctly scoped, by contrast: no archetype reads rival cash/cost/revenue (checked against §5.1's table and cross-checked that `commercial-engine` only reads settled gross, which is public per `bridge/industry.ts:66-68`, and `baseMarketValue`, confirmed fixed-at-worldgen and never mutated per 1350-F's own review note); no archetype computes a cross-studio rank or sort (row order in the manifest is the fixed registry `row` field, `hollywoodTypes.ts:9`, not a performance ranking); `talent-foundry`'s read of industry-wide credits to determine "who discovered whom first" is legitimate under the charter's own "shared public facts (catalogue, people's credits)" carve-out, not a read of another studio's private result.

**6. §7 failed-player dossier** — PARTIAL (design is sound; the dependency it rests on is not yet locked).
No conflict with "official Legacy boundary frozen at 2040" — the `CampaignLegacy = {official, endOfRun}` schema keeps the two fields independently nullable, so a post-2040 closure correctly writes `endOfRun` beside an unchanged `official`, and a pre-2040 closure writes only `endOfRun` (the player's run necessarily ends before ever reaching the freeze tick). This correctly serves ruling 3.
However: `1352-A` §7 explicitly labels the closure-week/end-of-run mechanics as "**Proposed** for Wave 4," and `1352-F`'s four adopted amendments touch only the condition state machine (transition table, counters, cover-measure proof, zero-fixed-cost loan edge) — none of them adopt or amend Wave 4/closure semantics. So 1353-A §7's assumption of a single well-defined closure week `C` is presently a shared sketch between two *un-adopted* proposals, not a locked contract. This is correctly gated (§4: Wave 5, behind "P15B Wave 4 charter"), so it is not a defect in 1353-A itself, but it is a coordination risk worth tracking explicitly rather than treating as settled.

**7. Ceremony §6** — MET WITH EVIDENCE on the mechanics; one forward-looking note.
- `SimStopReason` union and the exhaustiveness (`never`) guard confirmed exactly at `ui/src/engine/adapter.ts:2567-2586` and `:3120-3129` — adding a finale member will force a compiler error until a switch case exists, exactly as claimed.
- `LIVING_TURN_PAUSE_CLASS` confirmed exactly at `ui/src/lot/livingTurn.ts:97-104` (six members: release, scriptReview, castingReview, productionDecision, releaseReview, cashNegative) — note the actual file lives at `ui/src/lot/livingTurn.ts`, not `ui/src/engine/livingTurn.ts` as the task brief guessed; the charter itself cites only the bare filename, which is correct.
- "No pending decision or intent" confirmed against `bridge/session.ts:1007-1070` (the `studioDecision(state) === null` gate the charter says stays untouched).
- No player decision beyond what ruling 5/6 asked for: the design is a bare auto-pause (like `cashNegative`), not a forced-acknowledgment decision gate — correctly avoids inventing a requirement the Owner didn't ask for.
- Forward-looking note (not a Wave 1 defect): because the stop is a bare pause and the dossier is "available... any time after the freeze" rather than force-displayed, a player could hit Advance without ever seeing the ceremony content. Wave 4 (not yet chartered) should make sure the actual on-stop presentation surfaces the ceremony rather than letting it become silently skippable — a "ceremony" implies content the player is meant to see at least once.
- Q2 (audience-score label): **ACCEPT**. Using the frozen at-release score (types.ts:2571, confirmed) rather than the Industry page's live-recomputed score (`receptionVerdict.ts:103-107`, confirmed to recompute against *current* `state.market.segments`) is the only choice compatible with the charter's own frozen-forever/byte-identical guarantees (RED 11, RED 12) — a live score would make an old, "frozen" manifest silently drift as the market evolves decades later. The disambiguating label is the right transparency move.
- Q3 (no official Legacy for a save migrated past 2040): **ACCEPT**. Consistent with the existing no-backfill law (Law 7) and the identical precedent already set for the P15A.2 archive's `recordedFromWeek`. The alternative (a migration-time trigger) is explicitly and correctly rejected in §5.1 for inventing an unobserved Standing value. Note for release documentation, not a design flaw: any save already past week 6240 when this ships permanently loses the chance at an official Legacy — an unavoidable, one-time transitional cost of shipping the feature after the fact, correctly surfaced via `legacyEvidenceIncomplete` rather than faked.
