## Findings by question

**Q1 — Is R2 a genuinely selected, still-current, never-implemented Core requirement?**
MET WITH EVIDENCE. Companion §3.4 states the rule in full; §3.6 explicitly classifies "the busy-set refusal (R2)" as one of two hazards that "ride with the charge change and are Core"; decision register row R2 (`P14-PREPARATION-COMPANION.md:590`) restates it; §7.2 files it as Future-Ops-tunable *implementation form* only, not an Owner-open question. Current source confirms the gap: `src/core/actions.ts:2661-2699` (`applyReleaseTalent`) and `bridge/contract.ts:163-180` (`releaseRefusal`) check only "no contract" and "active screenplay task" — no seat check, no founding check. `tests/p14a1-firing.test.ts:59-63` records "R2 ... is NOT exercised here" with a named, non-evasive reason (out of that file's assigned Tests-1-9 scope, not overlooked).

The strongest later record is one the candidate document does **not** cite: `docs/engineering/playability-launch-review/plans/P14-HEADLESS-PLAN.md:1077`, the P14A.1 T2 coordinator ruling — **"R2 DEFERRED (release refused for the busy set / founding; companion recommendation not in A.1's plan text) — recorded for a follow-up."** This is the actual disposition event. It does not narrow or reject R2; it explicitly defers it *for a follow-up*, and `CONTINUATION-STATE.md:13` ("IN PROGRESS: R2 busy-set release refusal (a Core requirement never implemented...) is drafted for after the baseline") shows this task is that follow-up. Net effect: this strengthens, not undermines, the candidate's premise — but the candidate should have surfaced this specific ruling, since the task brief named that exact plan section as required authority and the omission leaves a load-bearing citation gap a later reader could mistake for an unexamined record.

**Q2 — Seat set correctness (director/cast/craft; writers via screenplay task; credited-only writers excluded; research excluded).**
MET WITH EVIDENCE. `src/core/productionPeople.ts:4-14` (`productionCompanyTalentIds`) and `src/core/employment.ts:126-128` (`activeProductionCompanyTalentIds`) union exactly director + cast values + craftIds of `state.studio.activeProductions` — the player's own productions, matching companion §3.4's "director, cast member or craft lead seated on an active production." `employment.ts:147-156` (`creditedWriterIds`) is explicitly commented "CREDIT ONLY — never union this into an availability test," confirming credited-only writers are correctly excluded and writers stay governed by the existing `activeWritingAssignmentIds`/screenplay-task refusal already in `applyReleaseTalent:2668-2676`.

Research exclusion is also correct. Decision-register row R2 itself defines the busy set narrowly as "any active production seat ... or a writing assignment" — no research. `employment.ts:161-172` (`busyTalentIds`) is the broader union used for casting/market eligibility and separately includes technology-project seats; `src/core/technology.ts:340-349` (`researchAfterEmploymentRelease`) is the existing P13B-designed lawful handler that pauses a research project when its seat's employment ends, and `applyReleaseTalent:2691` already calls it unconditionally today. Widening R2 to gate research release would be a real, uncited P13B behavior change; the proposal correctly declines to do that.

**Q3 — Founding predicate and whether a releasable contract can exist during founding.**
MET WITH EVIDENCE. `state.founding !== null` is the exact predicate used identically at ten other sites in `actions.ts` (lines 305, 852, 1194, 1257, 1944, 1971, 2450, 2468, 2552, 2737, 2887) — proposing the same idiom for release is in-house-style, not invented. And yes, a player can hold a releasable contract during founding today: `applySignContract`'s founding branch (`actions.ts:2552-2568`) appends a real row to `state.contracts` when hiring from the applicant pool. `applyReleaseTalent` has no founding gate at all currently, so calling `releaseTalent` on a founding-signed contract before `foundStudio` closes the draft is live and unrefused today. This is a genuine, reachable gap the proposal is right to close.

**Q4 — Bypass paths / stale-success assumptions.**
MET WITH EVIDENCE, no bypass found. `bridge/contract.ts:187-202` (`contractActionDecisions`), `:218-233` (`liveRefusal`, used by both quote and commit) and `:236-279` (`contractDraftToEngine`) all route through the single `releaseRefusal` function; `bridge/session.ts:1683-1690` revalidates via the same `conversion.refusal` at commit time before applying. Adding the two new checks inside `releaseRefusal` (as proposed) propagates to Profile, quote and commit without a second edit site — this matches the codebase's own stated design ("the sheet cannot disagree with the engine"). I found no second release-issuing code path outside `applyActions`'s single `case 'releaseTalent'` dispatch (`actions.ts:2956-2958`). Note in passing (not an R2 defect): the release confirmation copy at `bridge/contract.ts:303` still reads "half of the ... still guaranteed" — pre-P14A.1 50%-era wording, not the 26-week-cap language of companion §3.4's two disclosure branches. This is a pre-existing R1/disclosure gap, out of this proposal's stated scope, but the reviewer should not read the proposal's silence on it as new evidence that disclosure is already correct.

**Q5 — Persistence: "no save or projection bump" claim.**
DEVIATES — this is the one substantive defect. The proposal's item 7 states "No persistence change, no save or projection bump, no tuning constant." This is factually wrong for the Bridge layer as proposed. `bridge/schema/bridge-schema.ts:1753-1764` defines `CONTRACT_REFUSAL_KINDS` as a literal array (currently `unknownTalent, noActiveContract, renewalWindowClosed, unpublishedTerm, insufficientFunds, onScreenplayTask, underMarketCase`), consumed at `bridge-schema.ts:2139` as `refusal: nullable(enumeration(CONTRACT_REFUSAL_KINDS))` inside `StudioContractQuoteSnapshot` — a schema type that is generated into `bridge/schema/project-studio-bridge.schema.json`. `bridge/contract.ts:328` and `:598` populate that wire field directly from `refusal.code`. The array already carries a precedent comment at `bridge-schema.ts:1760-1763`: `underMarketCase` was added "P14A.1 (projection 42)" — i.e., adding a new refusal-kind literal to this array is the established trigger for a projection bump in this codebase. Adding `foundingDraft` and `seatedOnActiveProduction` to the same array (as proposed in "Proposed law" item 5) would change the generated schema's enum and, by the codebase's own precedent, requires a Bridge `PROJECTION_VERSION`/schemaId bump — contradicting the proposal's own claim. This needs correcting before implementation; it is a documentation/scope-declaration error, not evidence the underlying design is wrong.

**Q6 — Test plan sufficiency and neighbor-attribution rule.**
MET WITH EVIDENCE for soundness; PARTIAL for completeness against Q5. The listed cases (director/lead/antagonist/support/craft refusal with byte-identical state; post-release success; research-seat non-interference; founding refusal/allow-after-foundStudio; credited-writer-without-task allowed; Bridge `contractActionDecisions`/quote/command parity) are each derived from a specific §3.4/§3.6 sentence, not invented. The neighbor-attribution rule — grep every existing `releaseTalent` caller, attribute each newly-refused case by cause with old/new expectation, stage and review separately, never silently edit — is sound and matches this project's established "attribute stacked failures, stage by cause" discipline seen elsewhere in the evidence trail. My own substring grep of `tests/` found 35 files containing "releaseTalent" (some are fixture/provenance files, not test files); filtering to `.test.ts` files lands close to the claimed 29 — plausible, not independently reproduced, and appropriately framed as a future step for the test-author rather than a settled fact. Gap: the test plan has no case for the schema/projection consequence identified in Q5 (a new Bridge-side test asserting the projection bump and the new enum values reach the generated schema) — this falls out once item 7's claim is corrected.

## Verdict rationale

The seat-set law, the founding predicate, the engine/Bridge ordering, and the test derivation are all correctly reasoned from cited, still-current authority, and the codebase evidence backs every structural claim I could check. The one real defect is narrow, mechanical and precisely locatable: the persistence claim in item 7 is wrong for the reason given in Q5, with an exact precedent in the same file showing what the correct claim should say. This does not require reworking the seat-set/founding/refusal-ordering design — it requires one paragraph correction plus a Bridge test-plan addition.

**Required amendments (REFINE would have applied if this were the recommendation; recorded as corrections to land alongside implementation):**
1. Correct §"Proposed law" item 7: replace "no save or projection bump" with an explicit Bridge projection bump — new `CONTRACT_REFUSAL_KINDS` literals require regenerating `project-studio-bridge.schema.json` and bumping `PROJECTION_VERSION`/schemaId, per the `underMarketCase` precedent at `bridge/schema/bridge-schema.ts:1760-1763`.
2. Add the P14A.1 T2 ruling citation (`P14-HEADLESS-PLAN.md:1077`, "R2 DEFERRED ... recorded for a follow-up") to the candidate document's evidence trail, since it is the actual disposition record and the task brief specifically named that plan section as required authority to check.
3. Add one test-plan line: assert the new refusal codes appear in the regenerated schema and that `PROJECTION_VERSION` moves, mirroring the existing `underMarketCase` precedent test coverage.

Given the low cost and mechanical nature of these corrections relative to the otherwise well-evidenced design, my verdict is **KEEP** with these three amendments to be applied before or during implementation, not a blocking REWORK.
