## Verification by checkpoint

**1. Counter/transition step (`corporateCondition.ts:110–172`).** Exact match, confirmed by direct trace, not inference:
- First evaluation (`prev===null`, lines 116–117) synthesizes `{stage:'stable', since:facts.week, week:facts.week-1, ...:0}` and falls through into the *same* counter/transition code every other week uses — it is not a special-cased no-op, matching 1352-F2 ruling 1 exactly. Since every counter starts at 0 and increments by at most 1, no threshold (all ≥4) can fire on evaluation 1, confirming the stated property structurally rather than by assertion.
- `distressWeeks: stage !== 'distress' ? 0 : fired !== null ? 1 : distressWeeks` (line 169) is the precise, unambiguous resolution of the exact ambiguity I flagged in the original charter review (1352-B): `fired.to` can equal `'distress'` only via the `warning→distress` row, so "`stage==='distress' && fired!==null`" can only mean the entry transition — the override is correct and total.
- `assertCondition`/switch structure makes "at most one transition" a structural guarantee, not a runtime race.
- Row order within each stage (`stable`; `warning`: negativeRun-row before clearRun-row; `distress`: recovery-row before closed-row; `recovery`: warning-row before stable-row) matches 1352-A's original table and Amendment 2's replaced recovery rows line for line.
- `if (prev.stage === 'closed') throw ...('a closed studio is not evaluated')` (line 120) matches the absorbing/refusal requirement and the RED suite's `/closed/i` regex exactly.

**2. Causes (lines 134–151).** Every cause's `weeks` value comes from `lowRun`/`negativeRun`/`clearRun`/`distressWeeks` — never from `cash` or `cover` — so JSON-safety at `O=0` is structural, not merely tested. Per-row lists and order match 1352-F2's table exactly: `warningCauses()` conditional `[LOW_COVER, NEGATIVE_CASH?]` reused for both `stable→warning` and `recovery→warning`; `[negativeCash, lowCover]` unconditional and reversed for `warning→distress`; single `[coverRestored]` for the three clear-exit rows; `[DISTRESS_DURATION, NEGATIVE_CASH]` for `distress→closed`, using the pre-reset counter-step `distressWeeks` (the same local variable used for the transition condition, not the separately-computed `next.distressWeeks`). `publicCondition` (lines 201–203) returns exactly `{stage, since}`, nothing else.

**3. `coverWeeks` (lines 103–108).** `O = wfc + loanInstallment; O>0 ? cash/O : (cash>=0 ? +Infinity : -Infinity)` — exact match to §4.1.

**4. `remedies` (lines 182–198).** Fixed push order LOAN→REDUCE_OBLIGATIONS→RELEASE. Critically, `loanEligible(condition.stage, facts.weeklyFixedCost, {hasOutstandingLoan, founding})` (line 194) passes the *actual* `condition.stage` and the *actual* `capability.founding` — I read this line directly rather than inferring correctness from GREEN, and it genuinely forwards both values rather than hardcoding either, closing exactly the two blocking defects I found in 1352-D/D2. `REDUCE_OBLIGATIONS`/`RELEASE` correctly read only capability, no stage gate, matching §4.3. **Writer finding 1 (throw on a closed condition) — acceptable.** Neither §4.3 nor the pinned API states closed-condition behavior; mirroring `stepCondition`'s own absorbing refusal is a consistent, disclosed, fail-loud choice rather than a silent `[]`, and Wave 2 is explicitly tasked with ensuring a closed studio never reaches this call.

**5. `studioLoan.ts`.** `loanMaxPrincipal` (`floor(26·wfc/1000)·1000`), `loanEligible` (stage∈{warning,distress}, no outstanding loan, not founding, `max≥step`), the flat-interest `total` with a defensive `Number.isInteger` guard against future re-tuning, the `floor(total/term)+(i<remainder?1:0)` installment formula, and `loanInstallmentDue`'s `i=week-contractedWeek-1` — every formula matches my independently hand-verified values from review 1352-D exactly (smallest-total 1,120/28×22+24×21; boundary 14,560/52×280; boundary principals at wfc=38/39). **Writer finding 2 (`contractLoan` doesn't check eligibility) — acceptable.** The pinned signature (`contractLoan(principal, weeklyFixedCost, week)`) carries no stage/founding/outstanding-loan parameter at all — it structurally cannot check eligibility, and the brief's own throw contract for this function was always scoped to the principal law only. This is a correct Wave-1/Wave-2 boundary, not a gap in this deliverable, and the handback correctly flags that Wave 2's RED must pin the caller-side `loanEligible`-before-`contractLoan` sequencing.

## The reference check (read independently, not summarized from the handback)

`1352-E-refcheck.ts` is a genuinely rigorous, well-targeted script: it transcribes the law as an independent row table using an *integer* form of the cover comparison (`cash < warnCover·O` rather than `cash/O < warnCover`) — a real cross-check of the production's floating-point division, not a restatement of it — self-checks Lemma A by throwing if its own reference table ever double-matches a row, operationalizes Lemma B as a runnable predicate parametrized over five different `CORPORATE_WARN_COVER_WEEKS` values, deep-freezes every input before handing it to the real implementation (so mutation would throw), calls `stepCondition` twice per step for determinism, and fuzzes `remedies`/`loanEligible` across all four non-closed stages with random capability/wfc combinations specifically shaped to catch a stage- or founding-ignoring bug. Its self-disclosed limitation ("I wrote both the reference and the production code... not an independent author's reading") is honest and exactly the gap this review (1352-J) exists to fill — my own from-scratch derivations across four separate review rounds (charter, RED r2, RED r3, and now production) agree with it at every point I cross-checked.
