# Independent review 1353-D

RED review of the P15C Wave R retention guards and Wave 1 RED suite, against 1353-A (as amended by 1353-F and 1353-F2). Read-only; verified by tracing roughly two-thirds of the 62 Part B leaves and all 6 Part A leaves directly against the patch source (`1353-stage/1353-p15c-red-r2.patch`), independently hand-recomputing every archetype edge the task asked for, and cross-checking the dry-run output (`1353-X-partB-red-r2-run.txt`) against the handback's claims.

**VERDICT: REFINE**

Everything I checked was well-grounded and, with one exception, precisely correct — the hand-derivations are genuinely re-derived from the §5.3/§5.5 formulas (not copied from a nonexistent implementation), the injection proofs are real, and the fact-type shape has no cash/cost/revenue field or role flag anywhere. But I found one concrete, reproducible coverage gap in the archetype whose spec I was specifically asked to hand-check (`audience-institution`), plus a smaller completeness note. Both are cheap, targeted fixes, not a rewrite.

## (1) RED list coverage — one uncovered case found

I traced 1353-A §8 items 1–17, the 1353-F additions (13th-lens refusal, `legacy-closed-before-boundary`), the 1353-F2 additions (domainId tagging/RED 10, 8 lens-count leaves, RED 13's four-case table, RED 15's both-effects rule), and all four §5.3 amendment edges against their leaves. All 17 original RED items plus every named addition have a corresponding leaf that asserts non-trivially derived values (not just "does not throw"). One gap:

**Defect 1 (blocking, cheap fix).** No leaf anywhere in the 62-leaf file verifies that `audience-institution`'s `qualifying` refs are capped to **one best film per audience decade**, as 1353-A §5.3 states ("each audience decade's best film"). Both dedicated `audience-institution` leaves (`amendment-1-audience-institution-exactly-half-liked-qualifies` at patch line 2086, and the RED-15 no-events leaf at line 1939) construct decades with at most 2 scored releases, so "best film" and "every liked film" coincide there and can't distinguish the two readings. The coexistence fixture (`buildAllStarFacts`, line 1046) puts 3 liked films in one decade (weeks 10/20/25, all comedy, all `audienceScore: 80`) — exactly the case that would expose the bug — but `legacy-coexist-every-evaluated-archetype-held` (line 1104) only asserts `outcome === 'held'`, never `qualifying.length` or its contents for that archetype. **A plausible wrong implementation that pushes every liked release of a qualifying decade into `qualifying` (instead of just the best one) would pass all 62 leaves.** Concrete fix: add one assertion to the existing ALLSTAR-based leaf, e.g. `expect(archetype(manifest, 'ALLSTAR1', 'audience-institution').qualifying.length).toBe(4)` (one per decade) and that the three-film 192-decade contributes exactly its single best-critic/highest-audience film — no new fixture needed, since the data to catch this already exists in the file.

**Non-blocking completeness note.** RED item 4's generic "N−1 against N" requirement is only given its own dedicated boundary leaf for `artistic-voice` (`legacy-archetype-edges-artistic-voice-min-films-n-minus-1-vs-n`, line 781). The other four MIN-style thresholds (`audience-institution`'s `LEGACY_AUDIENCE_MIN_DECADES`, `genre-specialist`'s `LEGACY_GENRE_MIN_FILMS`, `commercial-engine`'s `LEGACY_MIN_FILMS`, `talent-foundry`'s `LEGACY_FOUNDRY_MIN_PEOPLE`) have no dedicated N−1-vs-N leaf, though the ALLSTAR/NONE coexistence fixtures land exactly at several of these thresholds (4 decades, 10 credits) as an incidental byproduct, and the two amendment leaves cover the harder fraction arithmetic directly. I'd want this closed before Wave 2 but wouldn't hold Wave 1 production for it.

## (2) Hand-recomputed archetype outcomes

I independently recomputed every case the task named, without reading any of the test's own inline comments as a substitute for doing the arithmetic myself:

- **`artistic-voice` at the share threshold** (line 801): `n = 100×5/25 = 20`. S-EXACT: `n=20`, `100×5=500 = 25×20=500` → held (inclusive `≥`). S-BELOW: `n=21`, `500 < 525` → notHeld. Confirmed correct.
- **`audience-institution`, calendar decades, mid-decade entrant + exactly-half liked**: for `amendment-1` (line 2086), decade A has `scored=2, liked=1` → `2×1=2 ≥ 2` → qualifies (exactly half does qualify, per the adopted rule); decade B has `liked=0` → `0<2` → does not. For `amendment-3` (line 2140), I recomputed `floor((1920+floor(w/52))/10)` for MIDENTRANT's 8 release weeks by hand and confirmed they land in exactly 4 distinct decade blocks (192/193/194/195), each with exactly 2 releases, all liked (`audienceScore:80`) — correctly `held`, and correctly unaffected by adding an unrelated INCUMBENT studio's own films (verified via the `canonicalJSON` equality assertion, confirming no cross-studio read). Both arithmetically correct — modulo Defect 1 above about `qualifying`'s cardinality not being pinned.
- **`genre-specialist` at exactly half**: `amendment-2` (line 2118), `n=8`, `comedy=4` → `2×4=8`, not `>8` → notHeld; `comedy=5` → `2×5=10>8` → held. Confirmed correct, and correctly the opposite inclusivity direction from `audience-institution`'s "at least half" — this is a real, deliberate, and now-precise asymmetry between the two archetypes, not a bug.
- **`technology-pioneer` own-adoption contrary**: `amendment-4` (line 2176). Studio X's adoption at week 426 (industry's first, `commercialWeek+10`) is a clear pioneer. Studio Y has a cancelled adoption (never operational) and its own late adoption at 716 (`416+300`, exceeding `416+260=676`). I confirmed the expected result: Y's contrary ref is exactly `['Y-LATE']`, never X's adoption (a cross-studio read, correctly forbidden) and never Y's own cancelled one (correctly excluded by the "non-cancelled" qualifier). Confirmed correct and precisely targeted at amendment 4's actual fix.
- **`talent-foundry` with an authored first credit**: line 900. P1's first-ever credit is on an authored film, then 10 later campaign credits with S; P2 (control) has the same 10 campaign credits with no authored credit. Expected `qualifyingCount=1` (P2 only), P1 absent from output. Confirmed correct against the charter's "authored films come first" disqualification rule.
- **Boundary cut, B−1/B, 6240 ranking inside / 6253 outside, in-run film at B**: lines 654–753. F-IN (week 6239, `<6240`) inside; F-OUT (week 6240, not `<6240`) outside — confirmed against §5.1's literal "below B" wording. The 6240/6253 ranking-snapshot leaf directly mirrors the charter's own worked example. The in-run leaf (F-RUN, week 6235, `inRun`) correctly counts toward `artistic-voice` (critic 90 ≥ 70) but is excluded entirely from `commercial-engine`'s settled pool (`s`), verified by `expect(JSON.stringify(engine)).not.toContain('F-RUN')`, and a malformed fixture that leaks a non-null `grossSettled` on an `inRun` film is asserted to throw — a stronger guarantee than the charter strictly required, but a reasonable and cheap one. All confirmed correct.

## (3) Part A guards — field exactness, injection proofs, budget

- **Field exactness**: I checked each of the six guards' asserted-field lists (patch lines 108–314) against the actual v1 predicates in 1353-A/1353-F. Every asserted field is one a v1 rule genuinely reads (e.g. root 3/4 correctly omit `TalentCareerEvent.criticScore`, whose own type comment says "recorded for context only" — I verified this exact comment at `types.ts:2572` in my earlier 1353-B pass; root 2 correctly omits `directCommitment`/`studioRevenueReceived` per §5.1's "Rival cash, costs, studio revenue — Never read"; root 5 correctly omits the intra-run gross curve since no v1 archetype reads it). I found no over-asserted or under-asserted field in Part A.
- **Injection proofs**: 1353-C's injection log (six distinct defects, one per root, each with an exact failure message pinpointing the assertion that catches it, each reverted and hash-confirmed) is a genuine per-root proof, not a claim. The documented "module-level one-shot flag is unsafe" finding (the harness runs `tick()` twice per week internally) is a real, useful, and correctly-diagnosed methodological trap that the author worked around with stateless conditions.
- **120s budget**: the number that actually matters — the real full-suite run of all 6 leaves in one process, which pays the campaign-build cost exactly once via memoization — was measured at **90.40s**, comfortably under the 120,000ms ceiling with ~25% margin. The higher numbers in the injection log (up to 189.9s) come from a different, more expensive methodology (isolated `-t` reruns that deliberately re-pay the campaign cost from a fresh process, sometimes bundling two leaves together) used only to *prove* each injection independently — they are not representative of the delivered guards' real runtime shape. Non-blocking note: machine-load variance already pushed an isolated rerun close to double the declared budget in this exact environment, so if CI hardware is slower or more contended than the authoring sandbox, the margin is thinner than 90.40s suggests. I'd raise `GUARD_TIMEOUT_MS` to something like 180_000 as a cheap hedge, but I don't consider the current number dishonest.

## (4) No rival cash/cost/revenue field, no role flag

Confirmed directly against the `LegacyFacts` type definitions in the patch (lines 418–491): `LegacyStudioFact` carries only `studioId, row, enteredWeek, closedWeek, standing`; `LegacyFilmFact` carries `grossSettled` (public, settled-gross only) and no cost/revenue field; no type anywhere has a `role`/`isPlayer`/`rival` field — provenance is carried only via the `domainId` tag (`playerFilms`/`industryFilms` etc.), which is data provenance, not a role flag, and the owner-swap leaf behaviorally proves it travels with a relabelled fact set. The structural leaf (`legacy-public-facts-only-structural-no-cash-cost-revenue-key`, line 1868) checks every fixture-helper's key set against `/cash|cost|revenue/i`, and the behavioral leaf (`legacy-public-facts-only-injected-sentinel-never-leaks`, line 1882) smuggles a bogus `rivalCash` field past the type system with `as any` and asserts the resulting manifest JSON never contains the sentinel value — a genuine behavioral proof, not just a type-level check. This fully satisfies check (4).

## (5) Over-specification

One minor, self-disclosed instance: `legacy-bounds-constants` (line 629) pins the exact **array order** of `LEGACY_ARCHETYPE_IDS`/`LEGACY_LENS_IDS`, which the charter's table order implies but never states as an API requirement. The test author explicitly flags this in-line as "this file's own reasonable reading... restated here so a reorder is RED too" — an honest, disclosed choice rather than a hidden over-reach, and cheap for the production writer to satisfy by construction. I would not block on it. I found no other instance of a pinned behavior the law doesn't state; the one place I initially suspected over-specification (RED 9's static-invariant substitute for "a ninth archetype refuses") is in fact the *correct* treatment given the parent-decided API shape (`buildLegacyManifest(facts, kind)` gives no caller channel to supply archetype identity), and 1353-F2 §3 explicitly and correctly adopted it as such.
