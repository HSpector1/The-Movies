## Requirement-by-requirement

**Cadence / window / lanes / points / ties (1350-A §3) — MET WITH EVIDENCE.**
- `isPowerRankingWeek(week) = week % 13 === 0` (patch line 87-89) — matches charter and 1342-O.
- Window `[W−52, W)`: `windowStartWeek = week − 52`; film skip `releaseTick < windowStartWeek || releaseTick >= week` (line 144) — right-exclusive, left-inclusive, matches `rank-window-edges` and is verified passing against RED r4 leaf `compute-power-ranking-window-edge-release-tick-w52-counts-w53-excluded`.
- Films: `filmScoreTenths` (lines 113-117) computes `round(CS·critic + (1−CS)·min(100,100·gross/(max(base,1)·SCALE)))` in one division. I re-derived this algebraically from the charter's two-step 0–10-scale formula (`10·(CS·critic/100+(1−CS)·reach)`, tenths = `round(10×that)`) and confirmed it collapses exactly to the shipped single-division expression — the single-division form is mathematically identical to the charter formula, just computed with fewer float operations before the final round, which is precisely the mechanism that avoids the 80.49999999999999→80 miscast the writer's F1 finding describes. FILM_CAP selection: sort by tenths desc, ties by ascending filmId (`compareText`, line 155) — matches the parent's tie-break decision, verified against the D/E tie-break leaf.
- Releases: raw `n` uncapped on the row, `releasesTenths = round(100·min(n,cap)/cap)` (lines 158-159) — matches.
- Points = `filmsTenths + releasesTenths` (line 167); rank = competition ranking (1-1-3) over ranked rows only (lines 175-178); presentation = ranked block by (rank, studioId) then unranked block by studioId (lines 179-182). I hand-verified the ALPHA/ZEBRA/MID/LOW and EARLY/MID/ABLE/LATE/ZOOM fixtures against this code and both match exactly.
- Eligibility: `available = originWeek ≤ windowStartWeek`; `ranked = available && enteredWeek ≤ windowStartWeek` (lines 126, 162) — exact match to charter wording.
- Band thresholds and precedence (cash≤0 → inTheRed even at zero cost; else zero cost → thriving; else floor(cash/cost) vs 13/26) (lines 96-105) — every boundary (12/13/25/26, cash=0, fixedCost=0) matches 1350-F's RED additions.

## Blocking defects

**1. TUNING comments state no numeric range, though the RED suite enforces one.** `1351-stage/1351-p15a2-production-r2.patch:197-203` (the seven `POWER_RANKING_*` comments, e.g. `POWER_RANKING_CRITIC_SHARE: 0.5, // critic score and audience reach weigh equally`) state only provisional rationale, never the bound. `tests/p15a2-power-ranking.test.ts:388-394` (as staged in `1351-stage/1351-p15a2-red-r4.patch`) asserts exactly these bounds: window/caps `>0`, `0<CRITIC_SHARE≤1`, `REACH_SCALE>0`, `THRIVING_WEEKS>STABLE_WEEKS`. This is the identical defect class the parent already ruled blocking on the sibling P15A.1 package the same day (commit `3b6cd98c`, "TUNING comment states the tested factor range [0.75, 1] (1346-J2 blocking note)"), and the review brief explicitly names this check (item 8). **Fix:** append the range each comment already implies, e.g. `POWER_RANKING_CRITIC_SHARE: 0.5, // in (0,1]; critic and reach weigh equally` and `POWER_RANKING_BAND_THRIVING_WEEKS: 26, // must exceed POWER_RANKING_BAND_STABLE_WEEKS`. Comment-only change, no logic touched.

**2. No RED leaf exercises any of the production's fail-loud validation paths.** `src/core/powerRanking.ts` (r2 patch lines 97-100, 121-124, 130-133, 139-143) throws on nine distinct malformed-input conditions (non-integer week/originWeek/enteredWeek/releaseTick, non-finite baseMarketValue/cash, duplicate studioId/filmId, out-of-range criticScore, negative/non-finite totalGross/weeklyFixedCost). I grepped the entire final RED file (`1351-stage/1351-p15a2-red-r4.patch`) for `toThrow`: zero matches outside the test harness's own internal `requireFn`/`rowFor` guards. The writer's handback (`1351-E-p15a2-production-handback.md:189-212`) reports these were checked only by an uncommitted throwaway probe script outside the patch — not part of the reviewable, re-runnable evidence trail. Given the charter's own "a snapshot is frozen and never recomputed" rule (1350-A §4), an unguarded NaN or malformed value admitted here would be permanent, so this guard is exactly the kind that needs a regression test, not just a one-time manual check. **Fix:** the test owner adds a small `describe('error handling')` block: one leaf per throw condition (or a parameterized table), plus one leaf asserting `financialStrengthBand`'s and `computePowerRanking`'s thrown messages never contain a probe cash/fixed-cost value (mirroring the existing `no-private-balance-probe` pattern already in the suite).

Both defects are cheap, mechanical, and don't require touching the law's logic — they are review-completeness gaps, not correctness defects in the shipped formula.
