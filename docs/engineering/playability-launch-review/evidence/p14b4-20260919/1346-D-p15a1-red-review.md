- Per-studio clamp scenario (`market-studio-window-clamp`): overflow case correctly produces raw `1.10` clamped to `1.00`; control case lands exactly at `1.00` without clamping and correctly expects `STUDIO_CLAMPED` false there — a genuine boundary distinction, not just "cap reached."

No wrong expectation found; no tolerance found that would mask a wrong constant.

## Check 3 — Symmetry
`market-owner-swap` swaps *which* studio owns fixed release ids X/Y (not just relabeling) — this would catch a bug that treats a specific studio id specially (e.g., index/order-based logic), since it changes which physical studio backs each release while structure (2 releases, 2 distinct studios) stays constant. `market-id-swap` compares results indexed **by studioId** after swapping which releaseId sits in which studio — correctly avoids the trivial trap of comparing by the swapped releaseId itself. `market-order-reversal` checks both canonical output ordering and full content identity regardless of input array order. `market-same-week-batch` checks the pre-batch-snapshot symmetry directly. All four genuinely constrain "no studio flag, owner or enumeration order enters the formula," not weaker proxies.

## Check 4 — Vacuity
**Significant gap (Blocking Defect 1):** no leaf calls `assessBatch` with a stock-lane exposure *and* asserts a hand-computed `windowTerm`/`stockTerm`/`pressure`/`factor` value. The only assessBatch-level test touching the stock lane, `market-pressure-decomposition-invariant` (`tests/p15a1-shared-market.test.ts:543-557`), only asserts `pressure ≈ windowTerm + stockTerm` — a tautology if production computes `pressure` by literally summing those two fields, which is the natural implementation. An implementation whose `assessBatch` silently drops stock-lane exposures (e.g., iterates only `lane==='window'` and never folds in `lane==='stock'`) would produce `stockTerm≡0`, still pass this decomposition identity, pass every window-only test (none of the other 25 leaves put a stock-lane exposure into `assessBatch`), and pass both harness leaves (which check determinism/step-bounds/active-set count, not per-assessment value correctness against ground truth — a deterministically-wrong implementation is still deterministic). `exposureWeight` itself is well-tested in isolation (Check 2), but that does not establish `assessBatch` actually consumes it for the stock lane. The explicit charter property "stock term ... unclamped: saturation counts volume" (distinct from the window term's per-studio clamp) is likewise never exercised. Additionally, 2 of the 5 reason codes (`WINDOW_RELEASES`, `GENRE_SATURATION`) are never asserted to appear anywhere (`NO_PRESSURE` and `STUDIO_CLAMPED` are checked by value; `market-reasons-capped-at-five` checks only `.length`, not the retained codes).

**Second gap (Blocking Defect 2):** `market-large-batch-linear-storage`'s "no co-batch list per assessment" check (`tests/p15a1-shared-market.test.ts:434-450`) only inspects **top-level** array fields of the assessment record (`reasons.length ≤ 5`). It never checks `reasons[i].sourceReleaseIds.length`. An implementation that keeps the top-level `reasons` array at 5 entries but embeds an unbounded, batch-size-proportional id list inside one reason (e.g. `GENRE_SATURATION` listing every same-genre batch peer — ~85 of 512 members at this test's parameters, ~6 genres) would pass the structural key/array-length check and, by rough estimate (≈1 bloated array of ~1,100 chars + 4 normal reasons + scalar fields ≈ 1,600–2,300 chars), plausibly stay under the 3,000-char ceiling too — the exact "co-batch list per assessment" defect the charter's annex L.5 exists to rule out.

Other leaves checked for vacuity and found sound: a trivial `factor≡1` implementation is caught by `market-one-player-one-rival`/`market-studio-window-clamp`; a `steps.count` never incremented is caught by `market-step-counter-basic` (`toBeGreaterThan(0)`) — though note the hostile-batch leaf's own step assertion (`toBeLessThanOrEqual` only) would tolerate `steps.count===0` in isolation, non-blocking since the sibling leaf covers it; `reduceExposures` no-op is caught by append/retire-boundary tests.

## Check 5 — API decisions in 1346-X
All three (retired-lane weight 0; `MarketReason={code,sourceReleaseIds,value}`; `reduceExposures` transition reference point = lane at `week-1` vs lane at `week`, no memory of prior calls) are consistent with 1323-A/F and D-1323-1; none touches a formula term. One documentation nit: decision 3's stated definition, read literally, would try to compute a "from" lane for a *brand-new* release at `exposureWeight(releaseWeek, week-1)`, which is `t<R` and throws per the same API's own precondition. The actual test suite resolves this correctly (`market-reduce-exposures-append` expects `transitions:[]` for newly appended members; `market-reduce-exposures-lane-transition` only uses pre-existing exposures), so the tests are unambiguous — but 1346-X's prose should be tightened for the production writer (non-blocking).

## Blocking defects
1. **`tests/p15a1-shared-market.test.ts:543-557`** (`market-pressure-decomposition-invariant`) — no leaf independently verifies `assessBatch`'s stock-term aggregation, the unclamped-stock property, or the `GENRE_SATURATION`/`WINDOW_RELEASES` reason codes. Required change: add a leaf (or extend this one) that calls `assessBatch` with a stock-lane-only exposure (no window-lane rivals) and asserts `windowTerm===0`, `stockTerm` against an independently hand-computed value (same closed form as `exposureWeight`'s stock formula), `pressure≈stockTerm`, `factor≈expectedFactor(stockTerm)`, and that the resulting `reasons` include a `GENRE_SATURATION`-coded entry; separately verify multiple same-studio stock-lane exposures are *not* clamped (unlike the window term).
2. **`tests/p15a1-shared-market.test.ts:434-450`** (`market-large-batch-linear-storage`) — the structural check only bounds top-level array fields. Required change: for every `reason` in `largeResult.reasons`, assert `reason.sourceReleaseIds.length` is bounded by a stated small constant (or equals the corresponding 32-batch reason's length for the same code), closing the nested co-batch-list gap.
