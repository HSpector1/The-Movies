# Independent review 1352-D

**Verdict: REFINE**

I independently re-derived every requested week table from the charter/amendment text alone (never trusting 1352-C/C2's arithmetic or each other), cross-checked the API surface against the brief field-by-field, and read the full 1,384-line r2 patch plus the parent's independent dry run. The hand arithmetic is exhaustively correct — including both self-caught off-by-one corrections, which I re-derived from scratch and confirm are right. The gap is coverage, not correctness: `remedies-two-routes` (item 9) never exercises two of the four inputs its own pinned signature takes, so a specific class of plausible wrong implementation would pass all 50 leaves at GREEN.

## Blocking defects

**1. `remedies()`'s `condition.stage` parameter is never varied away from `'distress'` — LOAN-vs-stage wiring is untested.** — Uncovered (Q1)
All five `remedies-two-routes-*` leaves (`tests/p15b1-corporate-condition.test.ts` lines 969–1040) call `remedies(distressCondition(), facts, capability)`, and `distressCondition()` (line 962–967) hardcodes `stage: 'distress'`. The pinned signature is `remedies(condition: Condition, facts: ConditionFacts, capability: RemedyCapability)`, and LOAN's eligibility is explicitly stage-gated (`loanEligible(stage, ...)`, stage ∈ {warning, distress} only — 1352-A §4.4, tested directly and correctly for `loanEligible` itself in `loan-eligibility-stage-table`). No leaf ever calls `remedies()` with `condition.stage` set to `'stable'`, `'recovery'`, or `'closed'`. A plausible wrong implementation that ignores the passed-in `condition.stage` for its LOAN branch (e.g. calls `loanEligible('distress', facts.weeklyFixedCost, capability)` with a literal string instead of `condition.stage`) would pass every one of the 50 current leaves, since all five `remedies-two-routes` fixtures happen to already be in `'distress'`.
*Fix:* add one leaf, e.g. `remedies-two-routes-stage-outside-warning-distress-excludes-loan`: a `stable`-stage (or `recovery`-stage) `Condition` with otherwise loan-eligible facts/capability, asserting the result excludes `'LOAN'` (while `REDUCE_OBLIGATIONS`/`RELEASE` may still appear per capability, since the charter doesn't stage-gate those two).

**2. `remedies()`'s `capability.founding` is never set to `true` — the founding exclusion is untested at the `remedies()` boundary.** — Uncovered (Q1)
Every `remedies-two-routes-*` leaf uses `founding: false` (lines 973, 986, 1001, 1013, 1025, 1033). `loanEligible`'s own founding-exclusion IS directly and correctly tested (`loan-eligibility-never-while-founding-or-closed`, `tests/p15b1-studio-loan.test.ts` lines 1235–1243), but nothing confirms `remedies()` actually forwards `capability.founding` into that check rather than, say, hardcoding `founding: false` internally. A wrong `remedies()` that never reads `capability.founding` would pass all 50 current leaves.
*Fix:* add one leaf, e.g. `remedies-two-routes-founding-excludes-loan`: otherwise loan-eligible `distress` condition/facts with `capability.founding: true`, asserting `'LOAN'` is excluded.

Both fixes are one small leaf each, reusing the existing `distressCondition()`/`fact()` helpers; nothing else in the suite needs to change.
