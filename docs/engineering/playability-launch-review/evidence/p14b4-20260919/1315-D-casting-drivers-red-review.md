- **Retro-minting on migration** — STRONG. `p14b9-save-v42.test.ts:143-153` explicitly loops every edge of the *released* (post-greenlight, post-shoot) genuine V41 fixture and asserts `sharedCompetitions === 0` and no new-kind driver anywhere — a retro-minting implementation would fail this directly. I checked this directly against `1315-X-production-draft.patch:118-167,319-373`: the draft adds a separate frozen `RELATIONSHIP_DRIVER_KINDS_V31` (5 kinds) and dispatches on `era === 42 ? **Gap 1 — repeat accelerator counting slots.** The P-dedup test (`p14b9-casting-competition.test.ts:345-353`) checks `sharedCompetitions` and the `castingCompetitionLost` count for pair (a,b), but **never asserts the absence of a `repeatedCompetition` driver** on that same write. Pair (a,b) is fresh at this point (`beforeCount` computed as 0 via `?? 0` — a first-ever competition, so `n=1`, no repeat driver should exist). A wrong implementation that correctly dedupes the *lost* driver to one-per-pair but computes the repeat accelerator's `n` from an internal per-slot count (reaching "2" within the same write, since the pair occupies two slots) would mint a spurious `repeatedCompetition` driver here, and this test as written would not notice.

**Gap 2 — "says nothing for a lower tier" (1313-A §4 item 3) is not actually tested.** `p14b9-casting-expiry.test.ts:248-270` ("names every Inseparable... says nothing for a stranger with no edge") only checks absence for `bystander`, who has **no edge at all** with the lead. It never checks absence for `support`, who — in that same test's `s` — has a **real, natural, un-elevated edge** with the lead from the shared take (confirmed by the file's own header, `:81-100`, "one shared take lifts a pair at most 6 points... reaching Inseparable needs many repeated collaborations," and confirmed structurally by test 3's own precondition check that this edge already exists to be varied). A wrong implementation that names *any* counterpart with *any* edge (not gated on tier === Inseparable) would still pass this test, since only the fully-elevated pair and the fully-edgeless pair are checked — the one case that would actually catch a broken tier gate (a real edge below Inseparable) is untested.

## Check 4 — Expiry INTERPRETATION leaf ruling

**Ruling: this is a lawful, in fact necessary, reading — not an invented rule.** 1313-F Amendment 4 (`1313-F-parent-casting-drivers-adoption.md:42-45`) requires the counterpart to be "on the player's roster **at the row's week**" — a future week — and states the check "restates... the employer-interval predicate... `rosterAt`." But `rosterAt` as it exists today reads only `endedWeek` (the early-release marker), never `terms.endWeekExclusive` (the natural, scheduled term end) — a gap the test-author correctly traced and named. "On the roster at a future week W" logically requires the contract to still be active at W, which requires checking *both* early release *and* the natural term boundary; a bare restatement of `rosterAt` alone structurally cannot answer this for a future week, since that predicate was evidently designed for "roster at the current tick," where a natural expiry would already be reflected by the engine. Reading "committed term reaches past the expiry week" as an additional necessary condition is a correct completion of Amendment 4's stated intent, not a new policy choice beyond it. I could not verify this in the parent's actual production draft (not in scope of this test review), so implementation compliance remains open, but the test's asserted interpretation is sound and should stand.

Caveat carried forward accurately by the authors: this specific leaf (`p14b9-casting-expiry.test.ts:272-283`) is **not currently a RED** on the unchanged engine — it passes vacuously today because *no* name appears in `detail` for any reason yet. Confirmed by the head log (`1315-X4-red-r4-dry-run-head.txt:19-22`): only the naming leaf fails; the other two expiry leaves (including this one) pass. This is honestly disclosed in three successive handbacks (C2, C3, C4) and in the file's own header — not a hidden gap, but the parent/coordinator reviewing the eventual recorded run should not mistake this leaf's current PASS for confirmation of the interpretation; it only becomes a real signal once the naming leaf itself goes GREEN.
