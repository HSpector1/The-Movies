## Correction to an earlier recommendation (per instruction to name these)

`1344-C3`'s "Additional finding" attributed the viable-control leaf's `0`-vs-`-0` `toEqual` failures to "P15A.1/P15A.2 code baked into the fixture's mint commit." **This is refuted by `1344-X6`**: those modules are pure and unimported by any tick path (grep: only comments in `tuning.ts` name them), so they cannot affect state. The parent's `1344-X6-negative-zero-probe.ts` shows the real cause is that live JS arithmetic can produce `-0` (six specific fields: `careerEvents[*].genreExpBefore`, four `genreExperience...perceived` values) while a save round-tripped through `JSON.stringify`/`JSON.parse` can never hold `-0` (`JSON.stringify(-0)==="0"`), so comparing a live state to a parsed fixture with `Object.is`-based `toEqual` is a method error, not a data error. **The fix landed by 1344-C3 (canonical key-sorted JSON comparison) is correct regardless of the wrong stated cause** — this is a documentation/attribution correction, not a functional defect, and 51/51 pass over step 5 under the corrected comparison confirms the fix holds.

## Non-blocking notes

1. **Chart-output timing edge case, not demonstrated but not ruled out.** The validator's chart formula uses strict `releaseTick<snapshot.week`; `markScriptProjectProduced` and the `h.films` append happen in the *same* tick as `releaseTick===week`. I could not determine from the diff alone whether a chart snapshot is ever computed in the same tick as a release that would land exactly on a chart-cadence week (a potential off-by-one where a film released this exact week would already show `status==='produced'` but validator's strict-`<` would not yet count it). This risk, if real, predates this patch (the old formula shared the identical race), and the natural-route test (`shelving-chart-output`) does pass on a real post-shelving chart week with the two formulas agreeing. Recommend: if the parent wants this fully closed, a bounded reproduction specifically constructing a release-week-equals-chart-week collision would settle it; I found no evidence it currently fails.
2. **`commissionHoldUntilWeek` has no validator bound.** The Save43 validator checks `integer(shelving.commissionHoldUntilWeek)` but not that it is `>=0` or consistent with a real shelving event. Production law always sets it correctly at shelving (`week+13`) and it's never touched elsewhere, so this is a latent validation gap, not an observed defect, and it isn't named as a required invariant in `1344-A` §4 or `1344-F2`'s additive list.
3. **1344-D3** (the dedicated re-review of RED r3's test suite, named as "next" alongside this review in `1344-X6`) does not appear in the evidence directory yet. I performed substantial independent verification of the RED r3 test file myself as part of this task (all four files read, cross-checked against source and against the charter's numbered test list), but a parent-tracked closure of that separate deliverable is still open.
