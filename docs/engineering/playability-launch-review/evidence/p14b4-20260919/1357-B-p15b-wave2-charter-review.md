## Blocking defects

**1. The charter omits the now-binding P15 domain-sequence and phase-triple requirement (1355-F2).** `1355-F2-parent-p15-domain-sequence-ruling.md` states explicitly: "This ruling ... binds the P15B Wave 2 charter (1357-A)," and rulings 1–3 require (a) one persisted allocator `p15Sequence:{version,next}` in the first P15 root to land, (b) that "each condition event and loan contract event" stores `p15DomainSequence` taken from it, and (c) that every P15 native row stores the phase triple `phaseId/phaseOrdinal/phaseOrderVersion` from `src/core/p15Phases.ts` (`p15b.condition` is already named in that table as "end of tick"). 1357-A §4's type sketches —
```
ConditionEvent = { eventId, studioId, week, from, to, causes, definitionVersion }
StudioLoanRecord = { loanId, studioId, lawVersion, contractedWeek, weeklyFixedCostAtContract, principal, total, installments }
```
— carry neither field, and §4's own identity justification cites "the 1356-F Amendment 1 pattern," which 1355-F2 ruling 5 explicitly withdraws ("1356-F Amendment 1's separate `nextRecord` is withdrawn"). Contrast 1356-F, which was amended in place with a "Later ruling" paragraph reconciling exactly this gap for the sibling charter. 1357-A's authority list (line 5-10) never cites 1355-F2 at all — confirming the charter predates it, as the task brief states — and none of its own R1–R9 questions in §12 surface the gap, because the charter was written before the ruling existed. This is not an Owner-tier question; it is a mechanical compliance gap against an already-issued cross-charter ruling, and it must be fixed (add both fields, wire the shared `p15Sequence` allocator into the same save step, add allocator-ordering assertions to §4.1) before RED staging, exactly as 1356-F did for its own sibling charter. Per 1355-F2 ruling 5's third bullet, `nextEvent`/`nextLoan` may still be kept for `eventId`/`loanId` identity (this resolves R9 below) — but that does not substitute for the domain-sequence/phase fields, which are a distinct, separately named requirement.

**2. A new `+` `loanPrincipal` rival money movement is not reconcilable with the frozen per-period sign validator.** §6.3's table requires the rival side to record `Principal | loanPrincipal | +`. But `hollywoodValidation.ts:295` reads, verbatim at HEAD:
```
for (const [kind,n] of Object.entries(p.movements)) number(n,kind === 'studioRevenue' ? 0 : -Infinity,kind === 'studioRevenue' ? Infinity : 0)
```
Every `RivalMoneyKind` other than `studioRevenue` is hard-bounded to `≤ 0`; `RIVAL_MONEY_KINDS` (`hollywood.ts:24-26`) has no positive-exception mechanism beyond that one hardcoded kind. If `loanPrincipal` is added to `RivalMoneyKind` as speced, the very first rival loan produces a state that fails `validateHollywood` and the tick throws. §4.1 ("Money") and §6.3 describe the reconciliation the validator should perform but never name the required edit to this line (add `loanPrincipal` to the positive-exception set alongside `studioRevenue`). This is the kind of gap RED staging would eventually surface, but a charter whose own §4.1 claims to specify validation exhaustively should name it. (The player side has no analogous per-kind sign validator — I checked — so this defect is rival-only.)

Both defects are narrow, additive fixes consistent with the charter's own design, not evidence of a flawed approach; I recommend REFINE rather than REJECT.

## Non-blocking notes

- **R1 (no registry field, departs 1354-P item 1):** justified. Nothing in the current tree yet implements a P12-style operating-state registry or an `isOperating` consumer (1354-P's own citations, e.g. `hollywoodTick.ts:312`, are from an older commit and land on unrelated code at c614b7e9), so there is no live consumer the omission breaks, and adding a field now would be exactly the "parallel registry" the annex (K.4 `corporate-no-parallel-registry`) forbids. Accept the departure, but the charter should say so as a closing amendment the way 1356-F closed its own R4, rather than leaving it an open note.
- **R2 (installments-paid derived, departs 1354-P item 2 literally):** the derivation `clamp(T−contractedWeek−1,0,52)` satisfies 1354-P's stated purpose ("price the remainder exactly") from already-persisted fields; accept.
- **Loan-model simplification vs RECONCILIATION-02 §4:** the research package's richer ladder (arrears, capitalization, Event-of-Default, acceleration) is a `[RECOMMENDATION]`, not Owner law; 1352-A §4.4, ratified by 1352-F before this charter existed, already deliberately supersedes it with "charged whatever the cash... no arrears or deferral state" for v1. 1357-A correctly inherits that decision (§6.4); this is confirmed continuity, not a gap 1357-A introduces.
- **§9 manifest right-sizing:** 1352-F explicitly delegated this exact judgment to this Wave 2 review ("Its review rules before any persistence code whether the argument stands"). Ruling: the argument holds for Wave 2. Wave 2's only cross-owner writes are two bounded, exactly-reconciled loan rows inside one atomic pure-reducer transition with a full-state validator — the structural substitute for the annex's chunked-manifest protocol that 1352-A §7 already established. The annex's stop condition (R: "P10/P11/P12 cannot provide... a chunked participant manifest") targets variable-size, multi-domain operating transitions (entry, dormancy, closure/settlement), none of which Wave 2 performs. It does not bind Wave 2; it does bind Wave 4.
- **Cash-timing trace (checkpoint 2):** I traced a loan contracted at week c through the tick convention (`currentTick`→`market.tick=currentTick+1`) by hand. This is not a bug: it is the charter's declared design ("cover means weeks of *next* week's obligations in hand," §3.2), it matches `studioWeeklyFixedCost`'s identical forward-looking framing inherited from 1356-A, and the probe's own shadow bookkeeping (`loanInstallmentDue(loan, W-1)` for the delta already charged) is internally consistent with it. No wrong-week-cash defect found. This is a paper trace, not a native run.

No bug found by reading.
