# Independent review 1355-B

Scope: `1355-A-p15a1-wave2-charter.md` at HEAD c614b7e9, checked against source at the same HEAD, the authority chain (1340-O, 1342-O, 1323-A/B/F, 1346-L), `src/core/sharedMarket.ts`, `tests/p15a1-shared-market.test.ts`, 1352-A §7, 1353-A, 1344-L. ## Blocking defects

None found. I traced the specific failure scenarios the brief named for fact 8 through source, not just through the charter's own citations:

- **operateStage** (`hollywoodTick.ts:78-91`, read in full): touches only shooting-workflow status (`assignShootingDirector`, `clearSceneryLoadIn`, `scheduleShootingTake`). It never writes `remainingTicks`. Confirmed.
- **remainingTicks decrement site**: the only decrements live in `operations.ts` (`advanceManagedProductions`, lines 1431/1614/1782), called once per business per week at `hollywoodTick.ts:376`, *after* the commitment loop at `:371-373`. The commitment loop gates on the picture's **pre-decrement** `remainingTicks`, so a picture at 2 this week decrements to 1 but is *not* committed this week — it can only be committed+released next week. This closes the "2→1→0 in one week" scenario the brief asked me to rule out.
- **Shelving** (`hollywoodTick.ts:260-302`): operates only on un-greenlit screenplay ordinals via `b.screenplayShelving`, never on `b.productions`/`remainingTicks`. Cannot fast-track an active production to Release Ready mid-week.
- **Research/technology** (`advanceRivalResearch`, `considerRivalSoundPurchase`, `createProductionTechnologyPolicy`): a full grep of every `remainingTicks` write site in `src/core` (save.ts reads, releaseAuthority.ts checks, operations.ts writes, hollywoodTick.ts:246 greenlight-to-8, actions.ts:366 player greenlight) turned up no other writer. None of the research/technology functions touch it.
- **Rival founded/entering mid-week** (the scenario the charter's own Wave-0 facts do *not* cite): scheduled rival entry runs at `tick.ts:1119-1122`, strictly *after* `finalized` is built (post-finalize, after `advanceHollywoodWeek` at `:935` has already run for the week). `enterRival` (`hollywood.ts:189-208`) always constructs the new business with `productions: []`. So a newly entered rival cannot contribute anything to that week's — or even the next several weeks' — release set (it must ramp a screenplay through greenlight at `PRODUCTION_TICKS = 8`, `tuning.ts:76`... actually `hollywoodTick.ts:246`/`tuning.ts:76`). No same-week risk.
- **Cancellation after the batch**: I searched for an active-production cancel path distinct from shelving and found none. The only "removal" of an in-flight picture is the P06A HOLD at `operations.ts:1754-1762`, which leaves it parked at `remainingTicks === 1` indefinitely rather than deleting it. There is no code path today that could desync the frozen batch membership from the actual releasing set other than a genuine implementation bug — which is exactly what the proposed witness at `hollywoodTick.ts:380-381` (extending the existing pattern) is built to fail loudly on.

Fact 8 holds. **Required addition, not a design defect**: §2 fact 8 should explicitly cite `tick.ts:1119-1122` and `hollywood.ts:195-204` (`productions: []` on entry) as the closing evidence for "a rival founded or entering mid-week," since the review brief named this exact scenario and the charter's own fact list is silent on it even though the code answer is clean. This is a citation add, not a rewrite — hence REFINE rather than REJECT.
