# Verdict: REFINE

Independent read-only review (Read/Glob/Grep) of `docs/engineering/playability-launch-review/evidence/p14b4-20260919/1313-A-casting-drivers-expansion.md` at repo HEAD `f8660266`, against its governing records (1312-A/1312-B/1312-F), the companion, the 647-A2/647-B and 1311-J precedents, and the cited source. No test, typecheck or runtime probe was executed — every finding below is a direct source/document read, not a native or behavioral result.

The core mechanism (driver law, Save42's central "no era-flag threading below V31" architectural insight, the numeric arithmetic, and the ordering/ownership plan) is sound and genuinely grounded in source reading. But the draft contains one governing-record deviation stated without acknowledgment, one wrong precedent citation, one real idempotence gap in a legally reachable game state, and one materially incorrect claim about which function supplies the Inseparable-expiry sentence's data. These must be fixed before RED is written.

## Required changes for REFINE

1. **Seam location contradicts the adopted governing record, uncited.** 1312-F Amendment 3 / drafting note 3 (`docs/.../1312-F-parent-relationship-adoption.md:35-39`) explicitly adopts the seam **inside `applyGreenlight`** (`src/core/actions.ts:291-359`), "not at the tick-tail delta seam" — and 1312-F is the byte-frozen, parent-adopted authority 1313-A itself says it expands under (1313-A:3). 1313-A's own Seam bullet (`1313-A:25-32`) instead places the mint call inside `applyGreenlightScriptProjectNow` (`actions.ts:2392-2399`), wrapping its internal call to `applyGreenlight` at `:2399`, and never cites or reconciles the change against 1312-F. I confirmed by direct read that `applyGreenlight` has exactly two call sites in `actions.ts`: `:2399` (inside `applyGreenlightScriptProjectNow`, carries `scriptProjectId`) and `:2945` (`case 'greenlight': next = applyGreenlight(next, action)`, no `scriptProjectId`). `requireGreenlightHeader` (`productionAdmission.ts:103-111`) throws whenever `development.mode === 'managed'` and `scriptProjectId === undefined`, and managed casting requires managed development (`castingSessions.ts:290-292`), so under any world where a casting session could exist, the `:2945` path is structurally dead for this feature — meaning **today** the two seam locations are behaviorally identical. But 1312-F's location is the more robust one (it automatically covers any future caller of `applyGreenlight`; 1313-A's choice would silently miss one). Fix: either move the mint call inside `applyGreenlight` per 1312-F, or add an explicit sentence naming and justifying the deviation, the same discipline 1312-B required of 1312-A for its own silent reversal (1312-B Check 1).
2. **Wrong precedent citation.** 1313-A:29 cites `recordCancelledAfterFirstTake`'s call site as `actions.ts:592-599`. The actual call is at `actions.ts:624` (`return playerStudioId === undefined ? withoutProduction : recordCancelledAfterFirstTake(breakPromisesOnCancel(withoutProduction, playerStudioId, cancelled), playerStudioId, cancelled)`); `:592-599` is an unrelated part of `applyCancel` (the productionId-not-found throw). This also means 1313-A does not reproduce the **actual** precedent pattern at that site: the caller derives `playerStudioId` from `state.hollywood?.playerStudioId` and skips the mint entirely when `undefined` (`actions.ts:621-624`). 1313-A's `recordCastingCompetition(state, studioId, production, projectId)` signature takes a `studioId` but never states this derivation-and-guard, needed since `greenlightScriptProject`/`greenlight` actions carry no `studioId` field (`types.ts:2610-2611`) and are implicitly player-only.
3. **Idempotence collision for a legally reachable slate.** `assertCastingSlateLaw` (`castingSessions.ts:121-142`) only requires each slot's own pair to be 2 distinct people and the whole slate to hold ≥`CASTING_MIN_UNIQUE_CANDIDATES` (= 3, `tuning.ts:1968`) distinct people out of 6 candidate-slots (`CASTING_CANDIDATES_PER_ROLE` = 2 × 3 slots, `tuning.ts:1967`) — it does **not** forbid the identical pair appearing as candidates in two different slots (e.g. `lead:[X,Y]`, `antagonist:[X,Y]`, `support:[X,Z]` is a legal slate). If a single greenlight seats X in both lead and antagonist, two genuinely distinct competition losses for the same canonical pair (X,Y) occur on one production. `RelationshipDriver` has no `slot` field (`types.ts:2250-2255`, whose own doc comment says "ref = the productionId") and 1313-A's idempotence rule is "(edge, kind, ref)" with ref = production id — so the second write collides with the first via the same `hasDriver(edge, kind, ref)` guard pattern used identically in `driveTake` (`relationships.ts:206-207, 241-251`) and is silently dropped, undercounting `sharedCompetitions` and suppressing a legitimate `repeatedCompetition`. The draft must either widen the idempotence key (impossible without a type change 1313-A doesn't propose) or explicitly accept and name this as a bounded limitation.
4. **The Inseparable-expiry mechanism claim is wrong.** 1313-A:41-42 says "the tier is read with the landed `tiersOnRoster`/`currentTier` at the row's week." `tiersOnRoster` (`relationships.ts:337-345`) returns **only** `readonly RelationshipTier[]` — a bare list of tier values with no counterpart identity — confirmed both by its implementation and by its only two existing call sites (`talentMarket.ts:915`, `:1196`), both of which only ever test tier membership (`.some()`/`.includes()`), never an id. Building "Mae Dunn works here and is Inseparable with them" requires the **counterpart's id/name paired with a tier**, which `tiersOnRoster` structurally cannot supply. A correct implementation must iterate `state.relationships` directly (filtered to subject + roster, each surviving edge paired with `currentTier(edge, week)`) — `currentTier` is reusable, `tiersOnRoster` is not, as stated. This must be corrected before RED, or a test-author will write tests against a function that cannot do what the draft claims.

## Notes for the follow-on RED/implementation (not blocking, matching the 645→647/1312 precedent of carrying items forward)

6. `pairChemistry`'s dormancy reason (`relationships.ts:373`, `'they have not worked together lately'`) is copy-level false for an edge whose only history is a lost competition (`sharedProductions: 0`) — they never worked together at all, "lately" or otherwise. Minor but real; worth a driver-aware dormancy sentence or a carve-out.
7. Cancel-then-re-greenlight of the same script project: `predictProductionId` never reuses a cancelled id (`actions.ts:362-364`), so a repeated cancel/re-greenlight cycle against the identical, unchanged casting-session evidence mints a fresh, distinct `ref` each time and is **not** silently dropped by the idempotence check — but this means the same underlying audition can inflate `sharedCompetitions`/`repeatedCompetition` without any new audition ever happening. 1313-A is silent on whether this is intended; name it explicitly.
8. Save42's `validateRelationshipsRoot(state, era)` needs to check era-31 driver kinds against a **frozen, separate 5-kind catalogue**, not a subset test against the live-widened 7-kind `RELATIONSHIP_DRIVER_KINDS` constant that `pairChemistry`/`counted()` also use (`relationships.ts:56-57, 372, 472`) — otherwise a bug that fails to strip new-kind drivers before delegating to the V41 chain would be silently accepted rather than refused, the exact risk 1312-B's Check 4 already flagged once for a naive widening. 1313-A's phrasing ("era 31... keeps... five kinds") implies this correctly but should say it explicitly.
9. `bridge/relationships.ts`'s `rosterAt` (`:100-112`) is not exported; per that file's own documented pattern (`:100-104`, "restated (not re-decided) here... Any change to the predicate there must be mirrored here"), `bridge/finance-upcoming.ts` will need to restate the same employer-interval predicate, not import it. Precedented, low-risk, but the draft should name it.
10. `counted()`'s exhaustive switch (`relationships.ts:163-171`) will need two new cases (`castingCompetitionLost` incrementing `sharedCompetitions`, `repeatedCompetition` a pass-through like `repeatedCollaboration`) or TypeScript's exhaustiveness check fails to compile — implied, not stated.
