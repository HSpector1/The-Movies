2. **When Codex instead of Claude?** RECOMMENDATION: (a) the handoff case above; (b) the independent review step the plan requires at every milestone, run read-only (Codex `read-only` sandbox, `approval never` for a non-mutating pass) so the reviewer is a different model and cannot write; (c) a second opinion on a compile diagnosis in M1a when the first repair class is uncertain. Not for parallel implementation on the same Unity project.
3. **Keep unity-mcp, adopt the first-party CLI, or combine?** RECOMMENDATION, in this order: (i) keep the pinned v10.1.2 exactly as it is through M1a, because M1a must measure the project as pinned; (ii) evaluate the first-party CLI and Pipeline package in a throwaway clone on the laptop (§8) without touching the real manifest; (iii) if the tests in §8 pass, adopt a bounded combination under a separately reviewed manifest change: the Unity CLI's direct commands as the agent's inner loop (`recompile`, `logs --console`, filtered `test`, `capture`), the CLI's MCP mode only for a harness that cannot run shell commands, and either retire unity-mcp or keep it only for tools the Pipeline lacks, after checking the two bridges coexist. Unity's deprecated in-Editor MCP (com.unity.ai.assistant) is not adopted. Not assumed: that the first-party path is better for this project; its skills are feature guidance of little value to a client that is mostly hand-written uGUI, IMGUI and UI Toolkit workspaces, and Unity itself says so for uGUI.
4. **Inspect scenes, read console errors, run tests, capture screenshots?** VERIFIED paths today: unity-mcp `manage_scene`, `manage_gameobject`, `read_console`, `run_tests`/`get_test_job`, `execute_code`, `execute_menu_item` (screenshot and play-mode tools UNVERIFIED in its reference); the project's own menu items through `-executeMethod` or `execute_menu_item` (`Studio/Automation/Capture Canonical A-B-C-D`, `Validate Canonical Scene`); the Editor's `-runTests -testResults`; the `ScreenCapture` API. First-party after adoption: `unity logs --console [--follow]`, `unity recompile`, `unity test --filter`, `unity command scene hierarchy`, `unity command capture game_view` / `capture screenshot`, `unity command editor.playmode start`, `unity command script eval`. Limit (VERIFIED): with compile errors the Editor is in Safe Mode and the Pipeline API is unreachable, so compile diagnosis must fall back to the Editor log and `-batchmode` exit codes (and "exit code 0 with compile errors" has been reported in Unity's issue tracker, so read the log, not just the code).
5. **Fastest reliable code → compile → inspect → repair → verify loop here?** RECOMMENDATION (durations to be measured on the laptop, never predicted): one Editor instance per project copy kept open so `Library` stays warm; edit under the single writer → the Editor recompiles (or `unity recompile --strict` once adopted) → read the console (`read_console` now, `logs --console` later) → run only the affected EditMode assemblies or a `-testFilter`/`--filter` set → fix → at a checkpoint the full EditMode suite with the exact attestation file names → PlayMode and the build only at milestone gates. Batch-mode relaunches per iteration are the slow path (Library re-import, single-instance rule); reserve them for the gates and the attestation XML.
6. **Avoiding agents fighting over the Editor, scenes, project files, resources?** VERIFIED constraints: one Unity instance per project at a time; unity-mcp serialises one command per Editor with a 30-second timeout and may repeat an effect on retry; the CLI refuses `unity test` on an open project and disambiguates several Editors by `--project-path`/`--port`. RECOMMENDATION: one writer owns the one open Editor (extend HEAVY-LANE-LOCK into an EDITOR-LOCK file named in the handoff); reviewers read source only, in a separate clone, and never open Unity on the writer's project; a second Unity Editor only on a second clone with its own `Library` (cost unmeasured; a single non-official source reports tens of minutes to regenerate; measure once); scenes and prefabs: commit before every agent session (the plugin README's own warning), set up `UnityYAMLMerge` (`unity vcs merge-setup`) before any two branches touch a `.unity` file, never let two sessions edit the same scene; never run `unity test`/`-batchmode` while the Editor has the project open; keep `UNITY_MCP_ALLOW_BATCH` unset unless a batch run is meant to own the MCP server.

Material: Unity CLI `recompile`, `logs --console`, `test --filter/--affected`, `capture`, `vcs affected`, `vcs merge-setup` (none exists in our tooling); the `unity-cli` skill as the agent's reference for those commands. ## 4. One recommendation and the proposed workflow

**Recommendation.** Keep Claude Code as the single coordinator-writer and Codex as the hand-over coordinator and read-only reviewer; run M1a on the project exactly as pinned; evaluate Unity's first-party CLI and Pipeline package in a throwaway clone on the laptop; adopt them for the inner loop only after §3.8 passes and under one reviewed manifest change; leave the attestation on the Editor's own `-runTests` XML.

**Proposed workflow (after that adoption; before it, replace the `unity` commands with the Editor's menu items and `-batchmode` gates):**
1. Session start: handoff resume; one Editor opened by the writer on the working checkout; EDITOR-LOCK written; reviewers in a separate clone, Unity closed there.
2. Inner loop per change: edit → `unity recompile --strict` → `unity logs --console --level error` → `unity test --filter <affected assemblies>` → fix; screenshots with `unity command capture game_view` or the project's `Capture Canonical A-B-C-D` when a visual claim is made.
3. Checkpoint: full EditMode with the Editor's `-runTests -testPlatform EditMode -testResults <EV>/contract-gate-editmode.xml -logFile <EV>/contract-gate-editmode.log` (Editor closed first; single-instance rule), classified against the M1a record; commit; HANDOFF.
4. Milestone gate: PlayMode (as M1b-P allows), `BuildMacOS`, the supervised `npm run play` run, the independent read-only review (Codex or an Opus reviewer), CF09 seal and, when the contract allows, the attestation.
5. Hand-over: HANDOFF.md written, Editor closed, lock released; the next agent reopens one Editor.

## 5. Compatibility limitations to carry

- No official 6000.3 statement for the plugin, CLI or Pipeline package ("6.0 or later" only). Pipeline is 0.9.1-exp.1, experimental; the CLI is beta (1.0.0-beta.14, 2026-10-21); either may change under us. Pin the CLI version used and record it.
- The CLI needs macOS 14+; this Mac cannot run it, so nothing here is pre-tested.
- Adopting Pipeline changes Packages/manifest.json (new package plus dependencies); that is a contract-adjacent change for the client and needs the CF09 reseal and a review.
- `unity pipeline install` is documented after `unity auth login`: the sign-in is the Owner's, not the agent's.
- Compile errors put the Editor in Safe Mode and sever the Pipeline API; keep the batch-mode and log-based compile check.
- unity-mcp's 30-second timeout and effect-repeating retries make it unsuitable for long test runs without `get_test_job` polling; its Codex HTTP setup is partly still an open PR.
- Only one Unity instance per project; parallel agents need separate clones with separate `Library` folders and the EDITOR-LOCK rule.
