## 2. Product tasks and three critiques

**Early DEVELOPMENT PREVIEW:** from the actual lot open Administration→Industry; identify one actual persistent rival; open a public person/employer and a disclosed project fact. If the project is private, “not announced” is the truthful public outcome, while correctness evidence traces the real internal project separately. No films or completed histories are invented. Save/Load proof follows when the persistence seam is implemented; preview is never completion.

**Causal core / Gate A:** follow a real project through lawful development, package/commit, production, post, release and result; inspect its people/credits/history after release. Explain why an employed person is unavailable, what constrained output, and which facts remain unknown. Inspect separate Standing/output lanes and factual recent activity. Exercise proposed opening/entry population through all nine in focused later fixtures; an opening-only candidate cannot pass rollout acceptance.

**Full ready integration / Gate B:** repeat the same task with activated charts/tendencies/announcements/History adapters and long lists. Reach the true last page and row, inspect same-name films/people, change sort/period, enlarge text, traverse Back to exact prior context and reconnect. Compare early and late population without imagined historical records.

One independent product critic sees actual screenshots and task/input evidence against §1 references, with equivalent data, viewport, text scale, navigation origin and state. At each of these three checkpoints return the **three largest actionable gaps**: evidence locator → player consequence → concrete remedy → same-task recheck. No self-awarded quality score or attractive-fixture selection. One optional extra polish round inside the ceiling. Critique is not a routine Owner approval wait.

Separate read-only correctness reviewer checks conservation, legality, visibility, identity, migration and source/build binding. One native-input owner controls foreground Unity/HID later; no simultaneous heavy jobs during input evidence. Use supported independent sessions, serially where needed, without huge fan-out. A source-only review is not runtime proof or enjoyment; unavailable independent support must be reported, not replaced by builder self-certification.

## 4. Warning-only completion check — specification, not installed

One project-local checker reads the **existing** task/milestone, requirement and evidence index, and the later execution log. The current preparation has a register and documentation evidence; an actual P12 execution index will be produced by the existing P11-style process. No second source of completion authority is created.

Input binding: active milestone/order, activated requirement IDs, required proof kinds, population/schedule/migration scope, exact source pair, schema/DTO/build identity, artifact hashes, evidence outcome, owner/reviewer provenance and explicit unchanged-scope reuse qualification. The checker compares to the execution order, not whatever scope the builder labels “done.” A finance test cannot satisfy arrival proof. Older evidence is usable only when its applicable unchanged scope and source/build/contract relation are explicit and checked; no 15-minute freshness rule.

On a COMPLETE claim, identify missing/failed/malformed/mismatched required evidence and emit one warning with missing IDs and relevant bindings. PASS text alone, a self-declared certification, wrong milestone, stale three-rival scope or unrelated source is insufficient. Warnings neither certify completion nor force continuation. On truthful PARTIAL/BLOCKED or Owner-stop, retain safe stop; do not demand more work. On fully matched evidence, say only no warning, never certified complete.

Bound checker execution to≤2 seconds, one local index read set and bounded output (recommend≤20 findings plus remainder). No network, paid service, suite invocation, gameplay, arbitrary commands from evidence, recursive subprocess, blocking exit/continuation decision, global config or extra memory framework. Deduplicate by milestone+requirement/proof+evidence fingerprint; changed evidence may emit a fresh warning. A repeated hook-active turn is suppressed. Timeout/parse/IO/checker exceptions must be visible as CHECKER_ERROR, never silent pass, with no automatic rerun loop. A dedup cache, if later needed, is disposable project-local runtime data outside simulation save; bounded per milestone.

Official sources checked 2026-09-10: [requested hooks URL](https://developers.openai.com/codex/hooks/) redirects to [official Hooks](https://learn.chatgpt.com/docs/hooks); [requested config reference](https://developers.openai.com/codex/config-reference/) redirects to [official Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference). Docs describe project-local hooks, trust review, Stop and `stop_hook_active`; Stop expects JSON, and continuation/blocking responses are available. **Those blocking/continuation responses are excluded here.** Supported documentation is not proof that the later selected client exposes warning output/trust flow. At later separately activated integration, check actual client/version capability against then-current official docs; use valid nonblocking output only. If unsupported, use an explicit milestone checker and continue safely. At most **one local hour**, inside the execution ceiling, no installation during preparation.
