## 3. Answer concrete player questions

For each reviewed task ask:
- What am I looking at and what is selected?
- What is happening now: active work, a real blocker, readiness, or normal waiting?
- Where would a player reasonably look for the next action?
- Is this inspection, a draft change, or a committed transaction?
- What will change and what will it cost?
- Did the input succeed, fail, or remain pending?
- Can I inspect supporting information and return without losing my place?

Review a representative opening state and a mature/multi-project state where existing evidence permits. Avoid diagnosing only the tutorial or only a developer fixture.

Prioritize these existing journeys:
1. Lot selection, camera, global navigation, time controls and returning from detail.
2. Script/casting/greenlight through production blockers, release and results.
3. People: candidate browsing/comparison, availability, lawful assignment and contract review.
4. Facilities: catalogue, placement, cancellation, construction and operational status.
5. Finance/Industry: meaningful summaries, drill-down, appropriate disclosure and return.
6. Campaign management: active campaign identity, Save, Save As, Load, switch, Quit and pending/error states.

Treat the Laboratory as one shared-interaction case, not a competing research-department design. Link Laboratory-specific findings to the P13B owner. Do not choose research briefs, change funding mathematics, or duplicate the P13B acceptance package.

## 4. Evidence discipline: no invented playtest

Do NOT launch the game, Unity editor, a build, test suite or native-input tool in this review. No process attachment, live application manipulation, player-profile access, save-file enumeration or campaign-library mutation is authorized.

Read already-existing screenshots/recordings only when available from the published package or explicitly permitted sealed evidence. Record build/source, capture date and frame/timestamp where known. An accessible local archive path is not itself permission to inspect it. Never search current user profiles for substitute evidence.

Label each finding:
- OWNER-REPORTED: exact quoted feedback, with its reported scope.
- EXISTING-CAPTURE-OBSERVED: visible fact at an identified frame; not proof of behavior outside that recording.
- SOURCE-VERIFIED: exact commit/path/symbol or lines establish the input/route/state behavior.
- DESIGN-INFERENCE: predicted player difficulty, not a measured observation.
- NATIVE-VERIFICATION-REQUIRED: a claim needing a future authorized session.

Do not claim measured task times, click-through, hitbox failure, hover behavior, visual crowding or latency from code alone. Source-derived click paths are not measured player click counts. ## 5. Recommend one coherent interaction pattern

Evaluate, rather than merely repeat, the existing world-first guidance. Preserve working routes. Recommend changes where evidence establishes a problem or supports a high-value hypothesis.

Cover:
- Local object selection and global list/notification entries reaching consistent inspectors.
- Appropriate compact inspectors versus deliberate comparison/workspaces.
- Stable action labels, ordering and primary/secondary/destructive hierarchy.
- Back/Escape/Cancel behavior, modal focus, text-entry key ownership and restoration of draft/selection/filter/scroll/camera context.
- Mouse-wheel ownership: panel scrolling versus camera zoom; pointer/trackpad behavior; supported keyboard/controller paths only.
- Valid/invalid placement feedback and a safe cancellation path. Dragging must not be the only way to perform essential tasks.
- Disabled reasons that identify the real constraint and offer the existing lawful route or explain that waiting is appropriate.
- Truthful cost/commitment review, immediate acknowledgement, pending state, duplicate-submit protection and safe failure/retry handling.
- Readable large text, long names, dense rosters, supported window sizes and status distinctions not dependent only on color.
- Attention levels, grouping repeated symptoms, actionable deadlines and direct navigation to the relevant subject.
- Brief dismissible first-use guidance and discoverable help, without an adviser that invents gameplay facts.

Selection must not sign, spend, demolish or advance time. Fewer clicks is not a reason to remove meaningful decisions, hide costs or alter a simulation rule. Do not invent a remedy command for a locked production, a false completion date, an automatic hire, a fake rival forecast, or an optimistic Save-complete state before persistence succeeds.

Keep visible charm and the lot; do not replace them with a disconnected dashboard application. Do not start with a component-framework rewrite, engine change, new tutorial campaign, new assets/audio system, heatmap platform or template platform.
