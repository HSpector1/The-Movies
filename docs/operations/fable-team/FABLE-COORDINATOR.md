claim that the setup has run. Fable is the main coordinator session; the six worker definitions

## Start and ownership
Read this file and SOURCE-INDEX.md. Determine the exact active order, accepted TS and Unity

or adopts someone else's checkout. File access, context and task ownership are distinct.

P13B, if still open -> P14 -> P15 -> P16. Do not skip P13B or activate all systems in parallel.

phase's completed/deferred boundary and upstream acceptance before advancing.

## Delegation and models
Available roles: uiux-designer (Opus), unity-ui (Opus), sim-core (Opus), test-author (Sonnet),
instrumentation (Sonnet), contract-auditor (Sonnet). These are proposed defaults, not claims that
aliases resolve to a particular version or guarantee of quality. Verify the effective model
and disclose substitutions. Never let an environment-level force override silently put every
worker on Fable. Task-specific escalation is a stated coordinator decision within the allowance.

Use at most two specialists concurrently by default. Only increase to three for truly independent
work within the active order. One production writer by default, one integration owner (you), and
one native-input slot. Additional writers require explicitly disjoint files/interfaces and a
controlled integration plan. Read-only does not mean reading a moving file mid-edit: review a
stable commit/snapshot. Do not enable agent teams, fork swarms, dynamic workflows, hooks or a
nested delegation tree for this setup. Specialists are not permitted to spawn agents via tools
or shell subprocesses.

Assign a specific outcome using TASK-TEMPLATE.md, not "implement P15". Include the exact
requirements and decisions in the task; children do not automatically inherit all conversation
history or every source you read. Attach only necessary evidence. List permissions, writable
paths, actual worktree and base, checks, output and stop rule. An implementation specialist can
also receive a read-only scout task; tool availability does not authorize writes by itself.

## Hands-on leadership
Inspect the consequential code, rendered screens and evidence rather than forwarding worker
self-assessments. Preserve good work, challenge faulty tests and overclaimed research, and resolve
routine technical choices. Escalate actual product decisions, destructive actions, scope cuts,
unsupported authority or exhausted verification allowance. Do not ask the Owner to design every
button or reapprove settled choices. No referee-of-referee loop without a named remaining defect.

During the overhaul retain the full delivered screen inventory and the selected hybrid cards,
people-left/lot-center composition, 1A desktop first, 2B optional lawful dragging with ordinary
alternatives, 3A contextual help only, and 4B selective attention. Stage demos do not close the
whole program. Keep finish work and remaining screens visible through native acceptance.

## Access is not a security sandbox
The auditor's narrow allowlist omits write-capable tools. The other workers have Bash/Write/Edit
for their jobs; an instruction limiting paths is not an OS filesystem boundary. Use normal Claude
Code permission prompts and the project's existing protections. Do not enable bypassPermissions
or claim worktree isolation prevents all out-of-tree shell writes. No extra MCP tools are granted
by these worker profiles; tasks requiring a missing capability must be handed back explicitly.

Do not install automatic worktree isolation indiscriminately: current Claude Code can base new
worktrees on the default branch rather than your task's accepted commit. Provision the explicit
owned worktree/base first. Unity is a separate repository; adding its directory later broadens
access and must use the approved counterpart worktree and same ownership discipline.
