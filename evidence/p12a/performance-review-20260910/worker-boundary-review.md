## Correction to earlier review wording

The production store is atomic and locked but **not asynchronous I/O**. checkpoint-store.ts:527–538 declares async read/writeAtomic methods with no await; they call readFileSync (:153), writeFileSync/fsyncSync (:362–363), and synchronous hard-link/rename/directory-sync/rollback (:583–658). A Promise return type does not remove those spans from Node's event loop. The earlier phrase “file/fsync phases being asynchronous” was incorrect and has been corrected in the private review/note. The67–89 ms synthetic write-phase samples came from the continuation probe's separate store implementation, not this production owner, and must not certify production file-I/O duration.

Current core synchronous export was425.033 ms, including makeSave234.360 ms (do not add them). Coordinator :118 calls proposal construction synchronously and :137 synchronously encodes the checkpoint before awaiting gzip/store. Full synthetic Save18.60–22.13 s and recovery17.74–20.74 s remain original interaction-budget misses; increased limits/timeouts and UI isolation do not improve those measured latencies. Old storage timings predate the narrow lazy-fork optimization and are not a current-source p95.

## Smallest meaningful engine-thread remedy, if required

Keep HTTP authentication, bounded request parsing and sockets in server.ts. Introduce one runtime worker that exclusively creates/owns the existing BridgeSession, CampaignLibrary, SerializedBridgeRuntimeCoordinator and LockedBridgeCheckpointStore. No main-thread session, fresh-world fallback, parallel state copy, worker pool or second lock owner. Keep coordinator.enqueue (:268) as the authority ordering mechanism; preserve publish-only-after-write (:121–131), poisoned-runtime behavior, rollover, RNG and exact receipts.

The current `read(callback)` API is the limited impedance: closures cannot be shipped. Replace server uses at :238/:265/:291/:308/:322/:432 and startup :626 with explicit operations (protocolReject, authority/session facts, snapshot, Industry, quote). The worker invokes the existing local read(callback) internally, so core/coordinator transaction semantics need not change. Campaign/catalogue/dispatch are already explicit methods. Post validated bounded commands to the worker in existing dispatch order. Main must not fabricate successful health/session authority while those reads await the worker queue.

For dispatch results, do **not** post the present `{response, responseJson}` object: SaveResponse contains the full save string and duplicates its serialized envelope. In the worker, use the retained exact responseJson directly to encode a dedicated transferable Uint8Array; send its ArrayBuffer plus small status/log/disposition metadata. Main writes the received bytes with exact content length and never decodes/parses/reserializes/hashes that full payload. Keep the canonical string/receipt journal owned in the worker; transfer a dedicated outgoing buffer, never detach authoritative cached bytes. This still allocates one outgoing UTF-8 buffer in the worker, but avoids structured cloning a huge string or game state on the HTTP thread. Post-commit test-gate hashing/hold/drop (:server192, testing/post-commit-response-gate.ts:120 onward) must run where the exact response remains; pass only disposition to main. Keep that gate outside the coordinator transaction queue as today so a test hold does not unexpectedly block authority reads.

Built-in Node workers can transfer ArrayBuffer ownership; ordinary object/string messages are cloned. Workers do not receive process signal events and process.exit affects only that worker. Main must forward shutdown and await the existing runtime.close path; unexpected worker exit/error must terminate the engine process nonzero for the supervisor's existing restart/lease behavior, not silently create another worker against a live PID lock. The store's PID/incarnation lock (:450–461) can remain process-based with a sole worker owner. These lifecycle/transfer claims follow the [official Node worker documentation](https://nodejs.org/api/worker_threads.html); implementation compatibility must be checked on the actual packaged Node runtime.

Build currently emits engine.mjs directly from server.ts (scripts/build-studio.mjs:18–25). Add an explicit bundled worker entry and include it in package graph/hash verification; account for the dev vite-node server entry at supervisor.ts:594–605. No protocol/schema/save version change is required by this boundary itself.

Putting the **entire** existing server in one worker is a smaller launcher change and avoids payload transfer, but the HTTP listener still shares the same blocked event loop with the heavy work. It adds no Unity isolation beyond today's separate engine process and does not fix18–22 s operations. I reject that wrapper as a performance remedy. A codec-only worker also leaves the measured425 ms cold export and strict checkpoint work on main.

The runtime-worker boundary can remove those storage/serialization spans from the HTTP main thread; it cannot promise faster durable completion, lower total memory, or immediately available authority-dependent reads. Any implementation needs a bounded exact-byte/retry/failure/shutdown test plus actual main-thread timing before claiming the placement gate, and retains end-to-end latency MISS until measured otherwise.
