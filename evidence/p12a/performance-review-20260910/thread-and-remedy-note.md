This is a read-only follow-up during root's native run8. No benchmarks, probes, native input, engines or source edits were started.

The exact pinned Annex Q wording is: “Any synchronous main-thread storage step exceeding 50 ms is a ship blocker; change the storage/caching architecture rather than loosening history retention.” Pinned Design §34 explains the original browser full-save rewriting/localStorage context. Do not silently redefine the condition, and do not infer a Unity frame stall merely from backend timing.

Unity is a separate process. `StudioBridgeClient.Industry.cs:66–82` yields the native network request, then synchronously parses the compact campaign receipt; catalogue/snapshot parsing also resumes on Unity's coroutine/UI thread. The reviewed traces do not time those Unity parse/layout frames. The legacy `/save` route carries a full save in its historical response; the named campaign route returns a compact receipt. Do not extrapolate compact-receipt UI cost to legacy full-save parsing.

Smallest staged remedy compatible with the current authority and atomic store:

1. Retain the already reviewed lazy campaign fork. Next remove duplicate work at the existing storage boundary: after a nested current checkpoint is strictly hydrated once, keep its exact canonical bytes and derive catalogue date/origin from that validated result; avoid rebuilding a BridgeSession, re-exporting it and importing it again solely for an inactive record's summary. Preserve genuine prior-schema migration and strict external-input validation. Use private owned validated results; do not expose a mutable hydrated object to two sessions or introduce a cache that survives object mutation/changed bounds.
2. Reuse one prospective validated checkpoint/encoding within one transaction for record creation, working checkpoint and response facts, instead of reconstructing/revalidating the same bytes repeatedly. Preserve all current/saved/journal digests, capacity checks, exact replay bytes and publish-after-durable-write behavior. Unknown external inputs still receive the full validator. Failure must leave the old authority and receipt set intact.
3. Replace sequential `gunzipSync` with bounded asynchronous zlib decompression while preserving prechecked per-checkpoint and aggregate limits, exact base64/checksum/UTF-8 validation and all-or-nothing publication. Avoid unbounded parallel decompression. This addresses zlib blocking only; JSON parse/serialization and strict core work still need treatment.

These local corrections should reduce redundant work and memory, but they cannot certify a50 ms engine-thread ceiling while a required cold export itself takes425 ms. Merely adding `Promise.resolve`, `async`, or a yield between whole records does not interrupt that synchronous call.

If the enforced gate includes the engine event loop, the smallest coherent isolation boundary is one built-in Node worker owning the existing session/coordinator and its heavy save/load/codec work, with serialized typed requests and bounded results to the transport thread. Keep the sole authority and production atomic store together; do not maintain a second mutable game state or split commit ownership across threads. Transfer encoded buffers for large exact payloads rather than cloning full GameState objects across threads: the old clone diagnostic already measured structuredClone around150 ms. This is a separate bounded implementation/validation change, not something to land during native input or claim already solved. A codec-only worker cannot remove the measured core export/validation spans.

If the gate is applied specifically to the player/UI main thread in the current separate-process architecture, demonstrate that placement with native frame/parse timing while the backend works, and record the explicit interpretation against the existing browser-context clause. Backend event-loop blocking and18–22 s interaction latency remain engineering/product issues even when Unity keeps rendering. Larger timeouts are recovery ceilings in either interpretation.
