## Authority and scope

Only the current issued task authorizes mutation. Apply, in order: explicit Owner instruction and rulings; applicable Current Ops execution order; accepted producer/consumer contracts and candidate evidence; the charter/register named by the order; then repository guidance. Report a material conflict instead of choosing silently.

Research, a pre-readiness package, a draft prompt, a technical KEEP, a roadmap, or an active branch pointer is not implementation authorization. Do not implement P-number scope unless the current task expressly grants it.

Work only on the assigned repository, base, branch, worktree, paths, and processes. `main`, `campaign/*`, accepted candidates, the Owner's durable profile, and active shared WIP are protected unless the task explicitly assigns them. Never infer edit permission from a discovery link.

## Simulation law

- TypeScript owns gameplay state, time, legality, finance, actions, identities, persistence, migrations, and random draws. Unity and browser surfaces present facts and submit intent.
- Keep simulation deterministic and seeded. Never use `Math.random()` for gameplay.
- Preserve pure-core boundaries: no React, DOM, async, or I/O below an authority boundary that forbids them.
- Use existing named constants and formulas. Do not invent defaults, thresholds, ordering, or parallel systems to fill an authority gap.
- Stable IDs are keys. Never join gameplay facts by display name, title, array position, or scene location.
- Treat save versions, schema/projection identities, migrations, generated consumers, and exact compatibility proofs as one governed boundary. Never fabricate history during migration.

The original build contract and later accepted mechanics remain source evidence; they are not erased. Apply each only through the current authority chain. Preserved former instructions and their exact provenance are under `docs/history/agent-configuration/accepted-2753e18/`.

## Research and reuse

Inspect current source and accepted contracts before designing. Reuse existing Project: Studio authorities, selectors, commands, projections, fixtures, and presentation patterns. Consult the canonical Mechanics Bible before changing original-derived behavior; if the authorized source is unavailable, record the limitation instead of reconstructing it from memory.

Keep product direction, implementation state, technical promotion, and Owner acceptance separate. Planning documents may constrain future work without granting permission to build it.

## Evidence and working practice

- State the plan before writing and keep changes within an explicit path allowlist.
- Use an owned isolated worktree. Do not switch, clean, reset, rebase, force-push, or rewrite someone else's work.
- Run the smallest relevant validation during development and the exact required gate before reporting completion.
- Report actual commands, commits, counts, failures, blocked checks, source access, and dirty state. Never claim a test, build, launch, visual inspection, playtest, or acceptance that did not happen.
- A generated UI, screenshot, browser run, Unity run, technical review, and Owner playtest are different evidence classes.
- Never use the Owner's durable gameplay profile as an onboarding or automated test. Native launch, Unity, bridge, supervisor, and HID require explicit task authority and a safe profile/process plan.
- Keep documentation/configuration-only work separate from gameplay code unless the task expressly couples them.

When authority is genuinely incomplete or contradictory, stop the affected mutation, preserve useful read-only findings, and return the smallest precise decision needed.
